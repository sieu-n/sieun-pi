# When the owner corrects a chat

Read this when the owner corrects how you work, whether about board shape, tone or what to report. Apply the correction now and make it hold for every future chat. The owner should never have to give the same correction twice.

1. Change the brief or a skill, because a local note or a local memory alone does not count. The refine-harness skill says which skill or AGENTS rule owns a general rule.
2. For a brief or code change, send the owner's exact words to the thread named `realtime layer` with `await agent_message.send(..., receiver_role="sibling", receiver_name="realtime layer")`.
3. Leave the harness refine to the service. When a turn that called `correction_add` ends, the chat service runs `/refine --global` in your session aimed at that correction, and when an owner message reads as a correction with nothing recorded, it sends one `[correction check]` line. Call `refine.run` yourself only for a lesson that is no owner correction.
4. In the same turn, call `correction_add` with the owner's exact words, a one-line rule, 3 to 6 theme key words and what enforces it. Reuse an earlier entry's theme words for the same thing. Set `enforcedBy` to brief, code or test (brief when you leave it out), and `ref` to the brief bullet, file, commit or test, or `pending <job>`.
5. When the work belongs to another thread, pass `handoff: {to, topics, with?, env?}`, where `to` is that thread and `topics` are the words its steps name. Put the rule's scope in `with` (the services it names) and `env` (`local`, `staging` or `prod`), so a check-in flags only steps in other chats that name a topic inside that scope.
6. When the tool says repeat, the earlier fix did not hold. Make the smallest change that gets agents to follow the rule, first a brief, skill or prompt line where agents read it before they act. When the owner says a rule should be enforced, he means agents follow it, and a code gate or refusal comes only when measured repeats show the text did not hold, with those repeats named in the fix (c81). Record the fix with its id.
7. A call counts as a repeat only when its theme shares at least two key words, and at least half of the shorter theme, with an earlier entry's theme, and its rule shares two key words with that entry's rule and theme. The generic words board, plan, title, note, step, goal, todo, thread, job, rule, agent, ci, repo and code do not count, so one-word themes never match.
8. When the owner gave a new rule that the tool calls a repeat of cN, pass `notRepeatOf: "cN"` in the same call or in a retry. The retry takes the false repeat back off cN.
9. When the tool records a new rule, it names the closest earlier rule. If the owner did repeat that rule, call `correction_add` with the new entry's `id` and `mergeInto` set to the earlier id.
10. To record a fix or retire a rule, call `correction_add` with its `id` and the new `enforcedBy` and `ref`, or with `status: "retired"`.
11. To reword a rule that does not match the owner's words, call `correction_add` with its `id` and the new `rule`, and his words stay as recorded.

A chat gets the rules in force as one `[corrections]` message at its first model call, and again after a compaction. A ledger change after that does not reach the chat until its next compaction. The block shows each rule as its id and the first sentence of its rule, reopened rules first. It leaves out a rule that the brief names by id, or that code or a test holds with no `pending` ref, unless that rule is reopened. Read one in full with `board.corrections("c12")`, or every rule in force with `board.corrections()`.
