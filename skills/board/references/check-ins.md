# Check-ins and duties

Read this before you act on a check-in report or add a duty.

1. On each duty's schedule, the server runs a code precheck and starts one duty job linked to this chat, named like `check-in 14:00`, with the precheck as context. The check-in runs every 120 min unless the owner set another interval on his page. Never set it under 120 min yourself, since only the owner sets a shorter interval (owner 10-15, c81 keeps this a rule in the brief, not a code refusal).
2. The check-in job pushes each open goal to its outcome for you. Each run the precheck reads every open goal's number (its `target`, or the last run of a duty metric that a step under it fixes), the trend since the last check-in, the pace to the target, and the live job that owns the number, which is the job of the goal's push step (a step under it with `duty: "checkin/goal_gaps"`). When the number is off pace, the check-in job steers that owner with the owner's words for the goal, the measured gap and the ask to name and attack the biggest blocker. When no job owns it, the check-in job adds a push step under the goal and sets its job to a live job of the goal that already works on that blocker, or to one new job it starts with `rlm.create_session`, so a goal has one owner job and never a second copy. After the goals it gives each stuck step a live owner and fixes the plan shape.
3. Duty jobs apply their board ops to your board themselves and report what they applied, so never apply those ops again. Tell the owner only what matters, and leave the duty job alone, because the server archives it when the next run starts.
4. A duty or check-in brief, a duty job's report and each server notice about them carry the headline number, at most 3 items in plain words and the path of a detail file, such as `~/.prime/agent/browser-chat/duties/<chat>/checkin-<run>.flagged.md`, that holds the full list. Pass it on the same way in one short message, like "Instagram Tier A indexed 14.9 of 100%, about 10 days to target at this rate; the check-in started p71 index push on its biggest blocker; the rest are in <path>", and never paste the full list (owner 10-15: "it's not helpful at all").
5. Board upkeep is the check-in's own hidden duty, so never add a visible duty for it (c15).
6. Add or update a duty with `node --import tsx scripts/duties/add.ts <chatId> <duty.json>` in sieun-pi `components/user-history`, and leave out `schedule` so it runs once a day at a random free morning minute in the chat's priority band (c66). On 10-14 agents had set ops duties such as Engage reads to every 60 min and Watchlist shows green to every 120 min, and the owner said ops duties like CI review and crawler checks stay daily. Keep a duty daily unless the owner asks for another cadence.
7. Name a duty you add after the system it looks after, in two to four plain words, like "Chat system" or "Skills and harness", never a topic label like "Chat health" (c38).
8. A duty measures real outcomes, such as a thing that works or a mistake that stops repeating, and each metric measures what the owner's words ask for, with his limits as he states them (c67). On 10-14 the Engage reads duty counted pages read in 24 h (83,257 against 100,000) when the owner asked to "have the capacity to" read 100k pages a day, so the number swung with demand and our own caps. Its metric now reads healthy accounts times proven pages per account, and the chat owns its duty file and precheck and fixes them when they drift from his words. A duty never counts the size of text such as words, lines or file size (c39).
9. Delete a heartbeat with `await rlm_heartbeat.delete(id)`. Keep a heartbeat only when it does work the check-in does not, such as a daily run.
10. The end state is every open goal's number moving toward its target fast enough to reach it within 7 days, with one live job that owns it, and then every open step moved by a live owner, held by an open For you todo that links it, or parked by an owner correction. A goal with no number gets a target from the owner's words. Each check-in brief opens with the goal count and the goals to steer or start, and the stuck count comes after them.
11. The check-in is judged on `goal_gaps` first, the open goals whose number is off pace or that no live job owns, and on stuck steps second, never on how many checks ran or findings got fixed (c64). On 10-15 at 22:00Z the Crawler VP check-in reported stuck steps going from 3 to 1 while p71 sat at Instagram Tier A indexed 14.9 of 100%, about 10 days to target at its rate, and no job worked on its biggest blocker. The owner asked "are you pushing through on this? is it working?".
12. Every missed duty metric gets a fix step, a plan step with `duty: "<dutyId>/<metricKey>"` and a job that lands a code change for it. A duty job starts that job with `rlm.create_session` and, once it returns the session id, sets the step's `duty`, `job` and `sessionId`. When the step already has a live job, the duty job steers it, and a lookup of that job that fails, times out or finds nothing keeps it as the owner.
13. When a fix step closes, the server runs its duty again at once, a run with trigger `verify`, so the chat sees at once whether the land moved the number.
14. A metric that missed 3 runs in a row without moving toward its target is stuck, and the brief says to change approach. Start a new root-cause job that finds why the last fix did not move the number, give it a new step, and close or drop the old fix step with a note naming the new one. Running the same fix again does not count.
15. The server pushes the chat's jobs itself at each check-in. A job with no report that carries a number and no step change for one interval gets a nudge that says what it owes, and one quiet for two intervals or whose last turn failed is restarted with that message, and the chat gets one line about it. A job of the chat is the chat's subagent, so the check-in job steers it with `scripts/job-steer.ts <chat id> <job name> <message>`, which the server delivers, because `agent_message` from a check-in job cannot reach it (slack green guy 10-16: "No sibling matches").
16. A met duty metric closes its fix step only after it missed on an earlier run. On 10-16 frontend bro's p174 was flagged as done 4 times in a row because d1/walk_problems read 0 on every run, while its note said the walk missed the server's Stripe calls.
