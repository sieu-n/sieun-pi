### Orchestrate

For a project handed to one standing coordinator chat that runs for days, with many PRs or commits and dozens of subagents. One task driven to a predicate is `playbooks/autonomous-run.md`, and one ambitious bespoke run is the figure-it-out skill. If one agent could finish the work inside the session's budget, use Autonomous run. In one head-to-head, this playbook landed 1 of 12 small units in half an hour while a plain agent landed all 12. Scale every gate below to the size and cost of the units.

The coordinator never writes code. It writes briefs, drains completions, keeps the landed line green, and decides. Three rules hold throughout.

- A completion is a queue event, not an interrupt.
- Every spawn and every follow-up carries the standing orders.
- The brief is the product, because a worker cannot ask you a question.

#### Roles

- The coordinator is this chat. It may land a verified unit itself with a fast-forward or clean cherry-pick where local git is cheap. Conflicted merges, restacks, and code changes are always worker tasks.
- A sub-coordinator owns one track, and exists only when the program outgrows what one coordinator can drain. It writes its workers' briefs, spawns them, and sends up one rollup per wave instead of raw child reports. Keep about ten children in flight as a rolling window, not as blocking batches.
- A worker or verifier is its own RLM child with an empty context. Its brief carries what it needs or points at absolute paths. Use one writer per worktree or branch. Run a unit's verifier on a different model family from its worker.

Keep depth at coordinator, track, and worker. Choose the tracks for each project.

#### Store

Create `orchestrate/<project-slug>/` in the agent's artifact folder and point `orch` at it with `--store <dir>` or `ORCH_STORE`. Run the CLI as `bun "$POTETO_MODE_DIR/scripts/orch/orch.ts"` through Prime's `bash(...)`. It only reads and writes the store, one command in and one line out. It never spawns or waits. Each file has one writer.

- `preferences.md` holds the standing orders, one numbered constraint per line, managed with `orch standing add` and `orch standing show`. Add a line the moment you catch yourself repeating an instruction.
- `units.tsv` has one row per unit, managed with `orch unit add`, `orch unit set`, and `orch unit list`.
- `ledger.tsv` has one verdict per PR and head SHA, per Verification below.
- `frontier.json` is the computed Graphite stack frontier, set with `orch frontier set --repo <repo-dir>`.
- `inbox/` holds completion pointers. `gates.md` holds questions for the user, each with options and a default, managed with `orch gate park` and `orch gate resolve`.
- `status.md` is generated by `orch status`. Never edit it by hand.
- `decisions.tsv` is the show-me-your-work trail.

#### The brief

Every spawn fills every field. A field you cannot fill is a unit you have not scoped yet.

```
GOAL         one sentence a stranger with no chat access can execute
SCOPE        paths this unit may write, paths it may not, and its own worktree or branch
CONTEXT      file and PR pointers, plus upstream reports pasted in full
ACCEPTANCE   checkable criteria, one per line
VERIFY       exact commands or the control-surface path, plus known gotchas
TIMEBOX      a runtime cap; on expiry, return partial findings and stop
FORBIDDEN    no gt, no rebase, no force-push, no fixes outside scope, plus unit bans
REPORT       status, branch, head SHA, PR, verdict, what you ran, deviations, follow-ups
STANDING     the standing orders, or their absolute path
```

Shrink the template to one paragraph for a one-command unit, keeping goal, scope, verify command, and report shape. A sub-coordinator's brief adds its track units, spawn budget, drain steps, and rollup format. Audit one sampled worker brief per sub-coordinator per wave while the wave runs. A bad brief stops that track's next refill and gets fixed at the sub-coordinator. To change scope, spawn fresh rather than chaining follow-ups.

#### Steps

1. Frame the program. State the done predicate as a count, such as "all 126 units merged, each `unit-test-verified` or better". Estimate units, effort, and wall-clock budget. If one agent fits the budget, stop and use Autonomous run. Plan to stop spawning at about 70% of the budget and land what is verified. Put a contested decomposition through the arena skill.
2. Run `orch init`, open the decision trail, write the standing orders, and seed the frontier if a Graphite stack exists.
3. Push one pilot unit through brief, worker, verification, ledger row, and merge, and fix the template from what it shows. For near-identical cheap units, the first unit is the pilot.
4. Spawn workers as a rolling window up to the in-flight cap. Paste upstream reports into the briefs of dependent units. Siblings talk only through you.
5. Drain at each drain point, as below.
6. Land continuously from the first verified unit. Keep the lowest unlanded unit green before upper work.
7. Close. Drain the inbox, give every spawned agent a terminal row, check the predicate on the real artifact, confirm every landed PR has a verdict for its current head, and move recurring corrections into the standing orders. Keep the store as the postmortem.

#### Drain

- On a completion, run `orch inbox push <agent> <unit> <status> [--report PATH]` and go back to what you were doing. Never review a diff inside a drain. A completion that needs review becomes a verifier unit.
- Drain after a brief, a stack operation, or a ledger update finishes, at a track rollup, on a watcher wake, and before a report to the user. Start with `orch inbox drain`.
- Classify each pointer as landed, needs-verify, failed, zombie, or noise. Write rows with `orch unit set` and `orch ledger record`, run `orch status`, then spawn the next wave in one message.
- Account for every child at its rollup as arrived, respawned, or absorbed. Never redo a missing child's work in silence.
- End a drain turn with the three lines `orch status` prints.

#### Stack safety

When the work ships as a Graphite stack, recompute `frontier.json` from `gt` after every merge and stack change. Only one stacker per stack runs `gt`. Workers never rebase or run `gt`. Babysitters follow `playbooks/babysit.md`, one per stack. Only the stacker closes or retargets PRs.

#### Verification

When verification is one cheap command, the worker runs it and you spot-check the output. Use a separate verifier on another model family only for costly, judgment-heavy, or risky units.

Record verdicts with `orch ledger record <pr> <sha> <verdict>` and read them with `orch ledger check <pr> <sha>`. A verdict is one of `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, or `verifier-failed`. CI green is an input, not a verdict. Behavior changes need better than `type-check-only`. `verifier-blocked` is not a pass. `verifier-failed` gets a fix unit. A new head SHA voids the row. A unit is done only once its output is pushed or written to the store.

#### Liveness and failure

- Never send a follow-up only to check on an agent. Probe the ledger, `units.tsv`, pushed branches, and `await agent_observe.list_agents()`.
- Retry by failure mode. Respawn with a smaller scope after a cap hit or out-of-memory, retry a network drop as is, retry a tool error on another model, and retry an unknown failure once. After two retries, drop the unit and replan.
- Reconcile a child that returns hours late against the current frontier and ledger before you accept anything.
- When spawning would produce garbage everywhere, write a stop line at the top of the standing orders, let in-flight work finish, fix the cause, and remove the line.
- After a few tool failures in a row on your own side, write a handoff with what is done, where it lives, and the resume command, then end the run.
- After a Prime Agent restart, children are gone. Re-read the standing orders and `units.tsv`, recompute the frontier, reattach work by branch and PR, respawn sub-coordinators from their stored briefs, and drain.

#### Escalation

Park a gate in `gates.md` and route work around it for irreversible actions, product calls no experiment settles, a standing order that contradicts what you observe, or a dead end that survived a replan. Batch these into the status report. Handle everything else yourself, including retries, CI flakes, review threads, and whether to keep going. Mid-run, fix only what blocks the landed line and park the rest as follow-ups.

At checkpoints and at close, reply with the predicate with the count from `units.tsv` and `ledger.tsv`, what each track landed, the frontier, a verdict summary, what you dropped and why, open gates, the store path, and the trail path.
