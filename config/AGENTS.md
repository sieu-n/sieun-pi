# Rules for every prime-agent session

1. Every reply, doc and commit message follows the unslop skill. Read its SKILL.md before your first prose. Never use em dashes, bold or `Label:` openers, decorative emoji, or "not X, it is Y" contrasts, and write each bullet as one full sentence.
2. A job runs as a subagent (`rlm.spawn`), with one subagent per unit of output, such as an article, page, module or account. The brief's `Split:` line decides the fan-out.
3. Open a new thread with `rlm.create_session` only when the user asks for a new or separate thread.
4. To steer a live job, message it with `agent_message.send(..., receiver_role="child", receiver_name=...)`. Never spawn a "-2" copy of it.
5. The browser chat renders markdown tables, mermaid blocks and `![alt](path)` images.
6. To wait for a CI run or a time across a turn end, call `board.wake(run=<id>)` or `board.wake(at=<time>)` and end the turn. Never leave `ci-run-status --wait`, `gh run watch`, a `sleep` or any other `bash()` handle, such as a sampler, running at a turn end, because it keeps the session's kernel and worker in memory for the whole wait. Start a long command that must outlive the turn detached, and never put `nice` in front of it. On a Linux box, start it with `systemd-run --user --unit=<name> --collect --same-dir -E PATH sh -c '<cmd> > <file> 2>&1'` and read `systemctl --user status <name>` and the file after the next wake. Never use `nohup` from `bash()` there, because on 10-18 two runs on us-metal02 started that way died with no output when their session ended its turn. On the Mac, start it with `nohup <cmd> > <file> 2>&1 &`. On a Linux box, start a big test suite or build, such as svelte-check, a full vitest or pytest run or a repo-wide tsc, as `heavy <size> -- <cmd>`, so the kernel kills only that run if it runs away. Use 8G for svelte-check or a tsc (peaks of 4.2 GB and 1.7 GB on 10-19 and 10-20) and 24G for a full Prime `packages/coding-agent` vitest run, because its default pool of 79 workers on this 80-core box peaked at 15.7 GB on 10-20, and two `heavy 8G` runs of it died at their own limit after 20 s. Where systemd is absent, `heavy` just runs the command. Pass `--test-force-exit` to every `node --test` run, because `--test-timeout` does not end a test file that passed but left a socket, timer or child such as an esbuild service open, and on 10-19 three such runs sat 85 to 168 min with no output as d7 hung calls.
7. Default to the simple, high-throughput option, and add no waiting rule, review round, safety gate or cautious setting (a country ask, an idle account, an avoided login, a held push, an arbitrary limit, a lane held at a level until a land or fix, a stop or pressure line another chat set) unless the owner asks for caution or a measurement shows the harm it prevents. Between 2026-10-12 and 2026-10-14 jobs asked GeoNode for a country, held proxy accounts on normal connection failures and treated a 50% Instagram pass rate as a problem, and the owner corrected it five times after c47 had said the same on 2026-10-12 (c60, c65, c71, c72 and c73 in the corrections ledger). From 2026-10-15 to 2026-10-17 the Crawler VP held census at 96, then 128 slots until a land because of metal's disk-pressure stop line, which nobody had measured, and the owner gave the rule again twice (c72, c100), so the board now flags a step that holds work until a land. Rule 7 covers a cautious setting you find in place as much as one you would add: a line, cap or pause that another chat, the chat that runs a box or an earlier job set is yours to raise or remove when the work needs it and no measurement shows the harm it prevents, and you tell that chat what you changed. Only a number the owner set himself stays, and you never assume he is deciding on a setting he has not named, because on 2026-10-19 a chat told its job "do not raise or remove that line, the owner is deciding" about a 1 MB/s write line another chat had set.
8. Rule 7 does not cover the few actions the owner keeps for himself, and each one waits for his answer on a For you todo:
   - An email, ticket reply, chat message or post to anyone outside waits for his ok, because a job emailed iWebFusion support on 2026-10-10 and a GeoNode dashboard helper sent "Connect me with human support" in GeoNode's Intercom chat on 2026-10-12 (c37).
   - A design he picked on the 5180 demo moves into the search app on 5174, staging or production only after he says 5180 is good enough, because a frontend chat read his pick as a go to ship on 2026-10-09 (c24).
   - A change to a variant he accepted goes into a new fork, because a job edited the Paper v5 watchlist in place on 2026-10-09 (c26).
   - A visible change to the board layout waits for his ok, because a job unfolded the goal requirements and targets on the board panel on 2026-10-09 (c33).
   - A running thread or chat moves to another host only when the owner asked to move that exact thread, and only through sieun-pi's `scripts/move-thread-host.py --owner-ask <his message id>`, because on 2026-10-19 a job moved frontend bro and slack green guy off his Mac on a broad "ALL" answer (c128, c131).

   A prod promote, merge or push to main needs no ok and no todo until the proper launch (c74, 2026-10-15). Draft the send or the move, ask on For you, and keep working on everything else meanwhile.

   A request to a vendor's support (GitHub, iWebFusion, GeoNode or any other) is never a send to draft or ask about, because the owner answered a For you todo that asked to send GitHub Support one request with "NONONONO" on 2026-10-19 after giving the rule on 2026-10-15 (c79). Solve the problem through the vendor's portal, its API, the box's console and SSH, and when no self-serve path exists, write the gap in the step's note and drop the support step. The board refuses a todo that asks to contact a vendor's support.
