# prime-relay

prime-relay is a small HTTP server that runs on every box and exposes that box's Prime daemon socket over the tailnet. It checks a bearer token on every request and knows nothing about sieun-pi, chats or other boxes.

## API

Every request needs `Authorization: Bearer <token>`, and a request without it gets 401.

- `GET /v1/health` returns `{"ok":true,"daemon":"answering"|"down","version":5}`.
- `GET /v1/daemon` with `Connection: Upgrade` and `Upgrade: prime-daemon` answers 101 and then carries raw bytes both ways to the daemon socket, so the JSONL protocol passes through unparsed. Two request headers change what goes back to the client. `x-prime-slim-snapshot: images` empties the image data in every attach snapshot chunk but the last (`slim-snapshot.mjs`). `x-prime-line-delta: 1` sends each `message_update` line after a session's first as copies of the previous update plus the new text (`line-delta.ts`), because the daemon sends the whole partial message with every token. `decodeLineDeltas` in the same file rebuilds the exact bytes, and HostBridge sets both headers. A `prompt` command from the client that carries `ownerTurn: <session id>` reaches the daemon at once without the field while this box's `pi-pool owner-turn` marks that session beside it (`owner-turn.mjs`), so the owner's message skips the turn queue with no extra wait. A `create` command that carries `relayFirstPrompt: {message, ...}` reaches the daemon without the field, and the relay sends that prompt to the new session the moment the create answers, then adds the prompt's result to the create's answer as `relayFirstPrompt` (`first-prompt.mjs`). A client on another box saves the round trip it would spend between the answer and its own prompt; a client whose answer lacks the field sends the prompt itself.
- `GET /v1/host` returns the box's CPU, memory and memory groups (on Linux each leaf cgroup's anon, shmem and swap from memory.stat and memory.swap.current, with the file cache apart; on macOS the pressure feed) and its own `pi-pool queue --json` and `pi-pool config` unparsed, from `host-stats.ts`; Settings > Hosts draws one card per box from it.
- `POST /v1/watch` takes worker pids, one per line, and returns `{"usable":...,"footprints":...}`: the box's usability reading (the raw pressure feed on macOS, PSI, swap-outs and runnable tasks a core over the CPUs the relay may run on, on Linux, from `host-stats.ts`) and those workers' footprints from sieun-pi's `worker-footprint.py`, which the install copies beside the relay. The chat service's watch reads every other box this way, so the worker totals and each box's Agent sessions cover every box. When the helper fails or passes its 30 s kill, the answer keeps the reading with `"footprints":null` and the helper's error in `footprintsError`.
- `POST /v1/lead` takes session ids, one per line, runs this box's `pi-pool lead <ids...>` and returns `{"lead":[...]}`, so those sessions' queued runs start first in this box's turn queue. An empty body clears the list, and a line that is no session id gets 400. The chat service on another box sends the chats that run here (`leadWriter` in legacy/prime/user-history/src/chat-hosts.ts).
- `POST /v1/pool` takes `{"key":...,"value":...}`, runs this box's `pi-pool set <key> <value>` and returns `{"pool":...}`, the box's fresh pool reading as `GET /v1/host` gives it. The key is `agent_queue_on` (0 or 1), `working_max` or `tree_working_max` (a whole number from 1 to 999), and anything else gets 400 without a pi-pool call. Settings > Hosts on the chat service sends it, so the owner changes every box's queue limits from the chat he has open (`relayPool` in legacy/prime/user-history/src/hosts.ts). A relay older than version 4 answers 404 here.
- `GET /v1/usable` returns the same usability reading alone. The chat service reads it beside `/v1/watch`, so a slow footprint helper on a loaded box never loses the reading.
- `GET /v1/history/<route>` passes the request to this box's pi-history socket as `/v1/<route>` with its query, and returns pi-history's answer unchanged (packages/pi-history). A search on another box reaches this box's index this way, with `local=1` so this box does not ask the others again. The socket is `$XDG_RUNTIME_DIR/pi-history/history.sock` on Linux and `~/.local/state/pi-history/history.sock` on macOS, and relay.json's `historySocket` overrides it. When pi-history does not answer, the route returns 503. A relay older than version 5 answers 404 here.
- `GET /v1/file?path=<absolute path or ~/path>` reads a file under the configured roots, by default `~/.prime/agent/sessions`, `~/.prime/agent/session-artifacts`, `~/.prime/agent/logs` (the daemon logs, so the chat host's resume pass sees this box's daemon restarts), `~/.prime/agent/browser-chat/prompts` (each session's last captured payload, so the chat host's Prompt view shows the payload a session on this box sent) and `~/.prime/agent/update-restarts` (each Prime update coordinator's record, so the chat host's d7 run books this box's update restarts as planned maintenance), and any other path gets 403. A path that starts with `~/` is this box's home. `Range: bytes=N-` returns 206 from offset N, `HEAD` returns the size, and a folder returns `{"entries":[...]}`.

## Metrics push

Once a minute the relay posts the box's CPU and memory split by group to the box's Alloy at `http://127.0.0.1:14318/v1/metrics` as OTLP gauges (`metrics-push.ts`).
They are `host_cpu_group_cores{group}`, the cores each group used over that minute, and `host_mem_group_bytes{group}`, each group's RAM.
The groups are the Settings > Hosts card's ids, and every group goes out each minute, at 0 when it used nothing.
Alloy remote-writes them to staging Prometheus with its own `box` label and `job="prime-relay"`, and obs.virev.ai reads them on datasource `estate_prometheus_stg`.
On macOS the CPU split comes from the pressure feed's `cpu_pct` per owner over its 10 s window.
A failed push logs one line to `relay.log` when it starts failing and one when it works again.

## Install

Run `node components/prime-relay/install.mjs --ref <commit>` from a sieun-pi checkout on the box. It copies `relay.mjs`, `host-stats.ts`, `rig-cpu.ts`, `cpu-groups.ts`, `kernel-read.ts`, `metrics-push.ts`, `slim-snapshot.mjs`, `line-delta.ts`, `owner-turn.mjs`, `first-prompt.mjs` and `legacy/prime/user-history/src/worker-footprint.py` from that commit to `~/.local/share/prime-relay`, writes `~/.config/prime-relay/relay.json` and a 0600 token file when they are missing, and restarts `prime-relay.service` (systemd user unit) on Linux or `com.sieun.prime-relay` (launchd) on macOS. The launchd job runs as `Interactive`, because launchd's default clamp left the relay at priority 20 on a loaded Mac and its footprint helper past the 30 s kill. The relay listens on the box's `tailscale ip -4` at port 7790 unless `--listen` or `--port` says otherwise.

The sieun-pi side lives in `legacy/prime/user-history/src/hosts.ts`. It reads `~/.config/sieun-pi/hosts.json`, opens `~/.local/state/sieun-pi/hosts/<host>.sock` for every other host so `new DaemonClient(path)` reaches that host unchanged, and reads remote session files with `readHostFile`. `sieun-pi hosts list|start|read|transcript` drives the same code from a shell.

## /v2/agents, the agent relay

`agents/main.ts` is the agent relay that runs as `pi-host-relay.service` on Linux and `com.sieun.pi-host-relay` on macOS, from the pi-host release tree, so it finds `ws` in that tree's node_modules. It serves every v1 route above through `createRelay`, and the same port also takes the `/v2/agents` WebSocket with the same bearer token. The frames are in `agents/protocol.ts`, and `apps/chat/docs/agent-model.md` section 4 has the design.

1. The chat server dials `ws://<box>:7791/v2/agents`. The relay opens one pi-host socket connection for the link and sends `hello` with the box's info, which holds its home, the project checkouts that exist and `agentsDir`.
2. After the server's `welcome {feedAfter}`, the relay starts pi-host's `durable_feed` after that seq and forwards each row as an `event` frame. The server keeps the cursor, and the relay only counts `ack` frames.
3. A `call` with a `durable_*` op goes to pi-host as that command, and its answer comes back as `result`. A command that never reached pi-host's socket answers with `unsent: true`.
4. A `watch` call opens a `durable_watch` and forwards its events as `watch_event` under the server's watch id, and `unwatch` closes it. `check` runs a wake's shell command with `sh -c` from home and answers `{ok, code, output}`. `box_info` answers the hello's info.
5. `file_get {path}` and `file_put {path, text}` or `{path, delete: true}` read and write files under `agentsDir` only, and any other path gets an error.
6. `instructions {cwd}` answers `{cwdExists, files}`, the AGENTS.md and CLAUDE.md files Prime loads for that cwd on this box and `~/.prime/agent/AGENTS.md`, each with its first lines, so the Agents page shows a Mac agent's files as the Mac reads them.
7. When pi-host's socket closes, the relay closes the link with code 1011, so the server dials again and sets up its watches after the next `hello`.

The relay also listens on `127.0.0.1:<chatProxyPort>` (7792 by default). Each request there goes up the newest live link as a `chat_http` call, and the server's result becomes the answer. With no live link, it answers 503 with a JSON error.

relay.json takes four keys beside the v1 ones. `piHostSocket` is pi-host's socket and defaults to `daemonSocket`, `chatProxyPort` defaults to 7792, `box` is this box's name in `~/.config/sieun-pi/hosts.json`, and `agentsDir` defaults to `~/.pi/agent/agents`.

Run `node components/prime-relay/agents/install.mjs --box <name>` on the box, with `--listen`, `--port` and `--pi-host-socket` the first time. It merges the flags into `~/.config/pi-host-relay/relay.json`, writes the service to run `node ~/.local/share/pi-host/current/components/prime-relay/agents/main.ts ~/.config/pi-host-relay/relay.json`, restarts the relay unit only and prints its health. The test is `node --test --test-force-exit --test-isolation=none components/prime-relay/test/agents-relay.test.mjs`, which runs a real pi-host child with a faux model against a fake chat server.

## Moving a chat to another box

Prime finds a stopped subagent through its per-box spawn ledger (`~/.prime/agent/rlm-ledger/<hash>.jsonl`), and a chat tree copied in from another box brings its children's files but no ledger edges, so the daemon answers `Unknown active session` for each of them. After the copy, run `python3 components/prime-relay/adopt-moved-subagents.py --apply` on the receiving box. It appends one spawn edge per child that has none, and it adds ` before move` to a child whose name the parent already gave to a fresh copy. Without `--apply` it only prints the edges, and a second run appends nothing.
