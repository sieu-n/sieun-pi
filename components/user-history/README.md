# Browser chat for Prime Agent

A thin browser front end for native Prime Agent sessions. `/what-did-i-say` and `/agent-chat` in the terminal start or reuse the shared server and print its URL. Nothing opens a browser for you, except `sieun-pi open` (see Mac app). Run `/reload` in the terminal after updating the extension.

Prime Agent owns every run, queue, name, model, skill and worker. The browser attaches to the daemon the same way the terminal's agents view does. Closing or refreshing a tab never stops a worker.

## What you see

- Sidebar: one list. A thread with an active or paused heartbeat or cron job (daemon `cron_list`) sits in the Heartbeats section at the top, above Needs response, in the same order as the other sections. A click on the Heartbeats label folds the section; a folded section shows a dot when a heartbeat needs a response, and the browser keeps the choice. The top row holds the search box (thread titles and tag names), two view icons and the Filter button. The list icon shows each card in full; the tag icon keeps the same threads, sections and order but shows only the tag chips on the second line (a card with no tag is one line). The threads below Heartbeats sort Needs response first, then Working (the daemon `rosterStatus` is running, the same Running section as the terminal agents view; a thread whose only work is running subagents is idle there too), then the rest by priority and recent activity, or, with the Chronological sort, as one list by recent activity. The Filter button opens the Agents view filters (status, tag, priority, progress, workspace, model) for the sidebar list and the sort choice; the button shows how many filters are on, and Clear resets them. View, filter and sort are saved in the browser. Needs response means the thread is not running, has messages, and had activity after you last read it in the browser. A thread you open keeps its Needs response place while it stays open and the tab is visible; it counts as read when you open another thread or the tab goes hidden. Each card has two lines. The first is the title with a spinner while it works or a dot when it needs a response. The second is the age ("3d", "2mo", nothing for a thread created today; or the heartbeat label and next run), the session cost from the native session usage ("$0.00" when zero, a dash when the daemon reports none), a short model name ("opus-5.5", "astra-6"), tag chips, a 3-step progress mark and a priority mark of 0 to 3 bars. Hover a card for its actions: add a tag, archive, and the menu (rename, priority, progress, tags, archive). Right click or Shift+F10 opens the same menu. Archive works like Ctrl+X in the terminal agents view, for any thread: one click kills the resident session ("Unknown active session" counts as done), records the native archived state in the session file, and drops the server's own attachment. The row leaves the list at once (the server holds it as archived until the daemon list agrees), an open thread hands the view to the next thread in the sidebar or New chat, and a toast offers Undo for 6 seconds, which records the session as active again (it comes back as a saved thread that resumes on reply). Archived threads sit behind a toggle. Drag the right edge to set a width from 180 to 480 px; drag it under 120 px and the sidebar snaps closed, the same state as Cmd+B. A click or drag on the closed edge opens it again at the last width. The edge also takes Left/Right, Home/End and Enter. The width is saved in the browser.
- Freshness: a running thread's mark comes from the native daemon summary the sessions stream already carries (no extra polling): `lastActivityAt` of the thread or of its freshest running subagent, the one-line `summary`, `lastHeardFromAt` and the failed worker state. Live (activity in the last 60 s) keeps the spinner; quiet (1 to 5 min) dims it and shows "quiet 3m"; stalled (5 min or more, or the worker went silent) shows an amber dot and "no activity 41m"; failed (the worker failed, or the daemon summary reports a failing model call such as "Model request failed", a usage or rate limit, "Try again in" or a retry, and the daemon judged that line at the thread's present message count, which it signals by sending `taskState`) shows a red dot and that line on row two, full text on hover. The daemon writes the failure line when a session settles idle on an assistant error and keeps it until its recap model replaces it, so a thread that ran on past the failure still carries the old line; without `taskState` the line is stale and the activity marks decide. The thresholds: a model call or tool streams events every few seconds, so a silent minute is unusual and five silent minutes means the run is stuck. The Agents view has a Stalled status filter and the same marks; the Subagents button adds an amber or red dot when a running child is stalled or failing, and each child row shows the same mark and text. In an open thread, the live work row's hover title shows how long the current tool call has run and when its last event arrived; after a silent minute the row shows "quiet 1m" in faint text, and "no event for 6m" in amber past 5 minutes. The line under the composer shows only what the work row does not: compacting, a retry, a shell command the user started, or queued messages. A thread that is not running but settled on a failed model call (the daemon sends task state "error" with the line) shows a red dot and the failure line in place of row two until a later message replaces it.
- Tags: one tag picker everywhere (the card, the thread header, the menu, and the Agents bulk bar). Type to filter. Enter creates the typed tag and assigns it, or toggles the highlighted one. Assigned tags show as chips on top; a click on a chip, or Backspace in the empty field, removes one. In the thread header a click on a tag chip removes it.
- Progress: a label next to priority with the values none, plan, implementation and qa, saved with the tags and priority.
- Agents view: the list button at the top of the sidebar, or Cmd+K, opens a full-screen table of every thread. Cmd+K again or Esc closes it. The header row holds search, filter menus (status, tag, priority, progress, workspace, model) whose options show their real marks (tag chips in their color, priority bars, the progress steps, status dots), a created date range with presets and a month grid, the Archived toggle and a Columns menu. Workspace and Created are hidden by default; Columns turns any optional column on or off and the browser keeps the choice. Agent messages, heartbeats and background command completions show as one muted line that also holds the turn's work. The header is one 40 px row: the title (click to rename: the field starts with the current title selected, Enter saves, Esc or a click elsewhere cancels, an unchanged or empty name sends nothing), the workspace, the tags with an add button, Priority and Progress (the bars and steps marks, with the value as text when the window is 900 px or wider; a click opens the same picker as the sidebar and saves at once), the Default and Questions switch, the subagents button and Archive. Questions lists every prompt, and a click jumps back to that turn in Default. In Default each turn shows the prompt, or a one-line trigger, and only its final reply. Messages that wake the agent after that reply (agent messages, background completions, subagent exits and failures, goal continuations, restart notices) never take the prompt's reply away. They fold into one row under it, "28 messages after this reply"; in the thread's last turn the newest one stays open with its reply, under "9 earlier messages". A model call that fails with no text after a reply keeps the reply and shows the error under it. Everything else in the turn (thinking, tool calls, interim messages, system notes, agent messages that arrived mid-run) folds into one collapsed row such as "Worked 6m 12s · 39 tool calls · 3 notes". While the turn runs, that row is one quiet line: a spinner, the current verb ("Running ipython", "Thinking", "Writing") with a light shimmer, the elapsed time and the tool's arguments in small mono; it stays collapsed until you open it. Open, the work is a timeline with a thin left rule: thinking in small muted text with a fade and a "more" button, and one row per tool call with its name, arguments, duration, and a red x only on a failure. Replies render as markdown with copy buttons. Web links (`http`, `https`, `mailto`) open in a new tab with no referrer; file paths and other link targets show as mono text with the target on hover. Tables sit in a bordered box that scrolls sideways when wide. A missing file shows as "Image not found: <path>". A ```` ```mermaid ```` block draws after the reply stops streaming and when it comes near the screen, in a sandboxed frame (see Diagrams below); a Diagram / Source switch and Expand, which opens it in a large dialog, appear once it has drawn, and a block that fails to draw shows its source with the error. The view switch has a third choice, Read: the thread fills the window with only the conversation (no sidebar, notepad, labels or work rows), a 720 px column and 16.5 px text. Esc outside a text field goes back to Default; the view is saved in the browser. Errors and stopped replies stay visible. When you scroll up, "Jump to latest" floats just above the composer and moves up as the draft grows; its x hides it until you are back at the bottom.

It opens a list grouped Running, Failed, Done and Cancelled, with a filter box and an All / Running / Finished switch. Each row has the status, name, short model name, cost and run time, and a second line: for a running child its native activity ("Running bash", "Thinking", "Writing") and latest recap; for a finished one its answer preview, the error line, or Cancelled. The menu matches a skill with or without its `skill:` prefix and by description, and it works on the new-chat screen too. - Account: the composer bar shows the thread's account by full email, with one meter per usage window in one style (label, percent, a 4 px bar that turns amber at 70% and red at 90%). ## How it works

```text
browser  <- WS api/ws, feed sessions --- Catalog: one DaemonClient, roster_subscribe, list all
browser  <- WS api/ws, feed thread ----- ThreadHub: one DaemonAgentConnection per open thread
browser  -> POST api/threads/:id/prompt  ThreadHub.prompt -> connection.prompt(...)
```

- `src/chat-catalog.ts` keeps the session list. It subscribes to `roster_update`, refreshes `list all` and `cron_list` after a short debounce, merges tags and priority from `src/chat-labels.ts`, and pushes the projected rows and tags to every open browser.
- `src/chat-threads.ts` keeps an attached connection per thread (up to 8 live, idle ones close after 3 minutes). On subscribe it sends one snapshot, then forwards native events. `message_update` is coalesced to one per 40 ms.
- `src/chat-projection.ts` trims payloads without renaming anything: tool output over 600 characters and long tool arguments get `truncated: true` and a fetch endpoint, thinking is cut to 240 characters, image bytes become `api/images/<hash>` URLs from a bounded memory store.
- `src/shared/thread-state.ts` is the reducer. The server and the browser apply the same events to the same `ThreadState`, so there is no polling and no DOM diffing.
- `src/shared/turns.ts` groups messages into turns for display. A user message always starts a turn; an agent message or background completion starts one only after the previous run settled.
- `src/shared/cache-health.ts` reads native per-call `usage` and flags broken caching.
- `src/usage/` is the Settings > Usage backend. `UsageService` (`service.ts`) starts one worker thread (`worker.ts`), so file reads, JSON parsing and DuckDB never run on the chat's event loop. The worker owns `<data dir>/usage.duckdb` (`@duckdb/node-api`, 2 threads, 512 MB memory limit) and answers `summary`, `series` and `models` requests. A usage failure never stops or slows the chat: a worker that cannot start or crashes is logged in one line and starts again after 10 s, doubling to 5 min; meanwhile the `usage` feed and `api/usage/summary` report ingest state "error" with the message, and `series` and `models` answer 503. `close()` stops the ingest, waits for the pass in flight and closes DuckDB; it terminates the thread after 2 s and returns after 3 s at most, so the chat's stop and its exit-75 restart never wait on DuckDB. The backend calls it on shutdown. The sources are the transcripts in tokscale's scope (`sources.ts`): Prime Agent root sessions and RLM children (`session-artifacts/<root>/sub-*/.../*.jsonl`), plus `~/.prime/agent/sessions-archive/**` (sessions moved out of `sessions/`, which tokscale does not read; call ids do not depend on the path, so a moved file counts once), Claude Code `projects/**`, Codex `sessions/**` and `archived_sessions/**` rollouts, Pi sessions, and the Hermes and OpenCode SQLite files, read whole when they change (`databases.ts`). `parsers.ts` ports tokscale's per-client rules: one Prime Agent call per assistant message with its own cost, Claude Code `message.id:requestId` merged across streamed copies, Codex `last_token_usage` per `token_count` with repeats and replayed fork history dropped. `prices.ts` keeps LiteLLM's price table in `<data dir>/litellm-prices.json` (fetched at most once a day, the cached copy when offline) and prices only calls whose source records no cost.
- Sync (`ingest.ts`): the first start reads every file once, newest first, so the recent hours appear early. Every pass works 140 ms and then rests 60 ms, so a build uses at most about 70% of one core, in the worker thread only. After that a recursive `fs.watch` per root marks changed files, a pass runs 2 s after the first change, and a sweep every 5 minutes stats the files of the live roots as the safety net for a missed event; the archives (Codex `archived_sessions`, Prime Agent `sessions-archive`) are swept every 6 hours. A sweep works 25 ms and rests 75 ms, so its stat calls never run as one burst. Each file is read from its saved offset; a shrink, a new inode, or changed bytes before the offset reread it from 0, which is safe because rows merge by a 64-bit key of source and call id. The calls of a batch and the file offsets they were read up to commit in one transaction, so a crash never skips or doubles a row. `usage.duckdb` is a cache: delete it, or change `schemaVersion` in `store.ts`, and the next start builds it again from the transcripts. Smaller changes avoid that full read: a new column is an `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` line in the schema, and a parser fix bumps that parser's `version` in `parsers.ts` (or `databaseVersion` in `databases.ts`). Each file row records the version that read it, so the next start deletes the calls and checkpoints of that source only and reads it again; a Prime Agent or Claude Code fix rereads about 6 GB instead of all 39 GB. The throughput figures (per second over 60 s, per minute over 60 min) come from an in-memory window of the last 61 minutes of calls, one count per token kind per call; per day (per kind) and the cost today come from DuckDB.
- `src/client/` is the Svelte 5 app. `src/client/ui/` holds the shared controls: `Floating` (top-layer anchored panel), `Select`, `DateRange`, `Checkbox`, `TagPicker` and the `tooltip` action. `src/client/usage.ts` holds the pure helpers behind Settings > Usage (number formats, the bucket per window, the chart layout, the sync line). `chat-assets.ts` bundles it in memory with esbuild in a worker thread (`chat-assets-worker.mjs`) once the service listens, and serves it with an ETag; the page and app.js wait for the build, the API answers at once. `chat start`, `stop`, `url` and `status` load prime-agent only when they need its default paths (about 1 CPU second).
- Diagrams: `src/chat-render.ts` serves `render`, a page embedded only as `<iframe sandbox="allow-scripts">`, and `render.js`, built on first use from `src/render/main.ts` with mermaid (about 5 MB). The sandbox gives the frame an opaque origin, so it cannot read the chat's storage or call its API, and the chat page keeps its strict CSP (it only adds `frame-src 'self'` and `https:` images). The frame has its own policy: inline styles for mermaid's SVG, scripts only from `render.js`, no network. `src/client/diagrams.ts` posts `{ type: "render", id, kind: "mermaid", source, theme }` to the frame and sizes it from `{ type: "size", height }`; wide drawings shrink to 70% and then scroll sideways. The second kind is `page`: `{ type: "render", id, kind: "page", html, theme }` carries a wiki page's HTML, which the frame parses with `DOMParser`, copies through a tag and attribute allowlist (scripts, styles, forms, embeds and inline SVG dropped with their content; `javascript:` links and non-https image sources removed), draws each `<pre class="mermaid">` with mermaid, and reports `{ type: "open", href }` for a clicked link and `{ type: "image", index, src }` for an image named by path, which the chat answers with `{ type: "image", index, blob }` from `api/local-image` (the frame's policy allows `blob:` and `https:` images). The `pageFrame` Svelte action owns one such frame. Another block kind (charts) is a new `kind` in the frame.
- `src/chat-pool.ts` wraps `components/pi-pool/bin/pi-pool` with argument arrays. `poolCommand` holds the exact command lines for off, on, rm and login. `AccountLogins` runs one `pi-pool login` child at a time: stdout JSON lines become the login state, a pasted code goes to its stdin, cancel closes stdin, then SIGTERM and SIGKILL follow; its own deadline backs up `--timeout 600`. It never runs `pi-pool-token`. It drops the calling session's variables, so pi-pool resolves only the thread named with `--session`.

## Chats

A chat is a thread kind: a Prime Agent session that is the owner's chat partner for one topic ("let's develop feature X"), created from the New chat screen with the Thread / Chat switch. It keeps the normal per-thread workspace (the repository it is responsible for), model, account, effort, name, labels and archive. It talks like a DM, does only quick read-only look-ups itself, keeps a board the owner sees (plan, owner todos, scratchpad bullets with links), and starts jobs with `rlm.spawn` (children in its repository) or `rlm.create_session(..., cwd=...)` (another repository), relays their reports, and forwards the owner's answers.

- Index: `<data dir>/chats.json` (`{ ids }`, newest first, an `IdIndex` from `src/id-index.ts`) is the chat side's one definition of "chat". `src/chats.ts` owns it. Rows in `api/sessions/stream` carry `chat: true` from it, so the sidebar sections chats apart. Archive from the sidebar works as for any thread and drops the id from the index. Undo (`POST api/threads/:id/unarchive`) keeps a chat a chat: the session file still carries the `chat_mode` entry, so `Chats.restore` puts the id back in the index, pins the chat and sets steering `all` again. A plain thread stays plain. The board file is not touched by archive, so it comes back as it was.
- Mark: the server creates the session with `config.extensionFlagValues: { chat: true }`. `extension/index.ts`, at `session_start` of a depth-0 session with that flag and no mark yet, writes the session entry `chat_mode` (`pi.appendEntry`), and on every later start finds it with `ctx.sessionManager.getEntries()`. The entry is the agent side's one definition. Children (depth 1 and deeper) inherit the flag through the runtime config but never get the entry.
- Brief: the extension registers the tool `chat_board`, whose `promptGuidelines` carry the chat brief (`CHAT_BRIEF` in `src/chats.ts`: the owner is the CTO and the chat the VP for its topic; DM voice, an owner reply of at most 3 short sentences or 60 words including bullets (an explanation goes to a wiki article page and the reply is one or two lines with its link; every board the tool returns opens with that rule, `REPLY_RULE`), a status answer one line per goal, leading with the answer; markdown renders in the chat, images and mermaid diagrams allowed; quick read-only look-ups only, every real task goes to a job; each job brief opens with the owner's words verbatim, then `My read:`; keep the board current; the scratchpad is short bullets with links; decide everything a VP can and ask the owner only for product direction, money, irreversible or external actions, and credentials or logins, at most 3 open asks, each one short question with 2 to 4 `choices`, the recommendation first; on a wake-up the owner did not start the turn's text is only the chat's notes (the feed folds it) and the owner hears from it only through tell_owner, at most once, when a goal finished, something is blocked or a decision is needed, see Feed; a step stalled 2 h or more changes at that check-in (a chase, a job, one owner todo, or `waitUntil`/`waitFor`); every goal gets its phases as child steps from the start (Plan, Decide only when the owner must choose, Build, Verify), each with its real status and its job on the step; on a `[check-in]` make the board match reality and start the next ready step, chase a stuck owner at most once and replace it with a job at the next check-in or when its last turn failed, and never ask the owner to relay a message; an owner correction to how the chat works goes to the `realtime layer` thread or `refine.run()` so it holds for every future chat). In a marked root it adds the chat tools (`chat_board`, `tell_owner`) to the active tools (`pi.setActiveTools`), which rebuilds the base system prompt, so the brief reaches agent-message wakes and heartbeat turns, which skip `before_agent_start`. Children drop the inherited tools. A job of a chat gets one line of its own: at `session_start` a depth-1 session whose parent session file carries `chat_mode` (`fileChatName` reads the parent's name from the head of that file), or a depth-0 root that `<data dir>/chat-jobs.json` lists by its session name, registers the tool `job_reply`, whose one guideline (`jobReplyGuideline`) says it is a job of that chat and, when it finishes, fails or gets blocked, must send its report to the parent (or the chat) first, since that is how the board updates, with `receiver_role="parent"` (a subagent) or `receiver_role="sibling", receiver_name=<chat>` (a root), at most one progress message before it, and a report written for a reader (the answer first, `##` headers, a table for numbers, a mermaid diagram for a flow, a link to any wiki page it wrote, which the reader draws under the report). The chat's extension writes `chat-jobs.json` on `tool_call`, from the plain string `name=` of each `rlm.create_session(...)` in the cell (`createSessionNames`; entries older than 30 days go on the next write). A root named after its `session_start` looks again at its first `before_agent_start` and adds the line to that turn's system prompt.
- Feed: the chat reads like a DM between the owner and the VP. Who started a turn decides what shows (`chatLines` in `src/shared/chat-feed.ts`, tracked the way `buildTurns` does: a user message, `[board] ` lines included, starts an owner turn; an agent message, a check-in, a job notice or a background completion starts an agent turn when the last run had settled, and joins the running turn otherwise). On an owner turn the chat's text shows as bubbles, as does a streaming reply. A finished owner-turn reply over 60 words shows its first 60 words, then "…" and a "More" button that shows the whole reply in place (`foldReply`, `REPLY_FOLD_WORDS`; words inside code fences, such as a mermaid diagram, do not count, and a cut never falls inside a fence); `tell_owner` bubbles never fold. On an agent turn its text never shows; the only way the chat reaches the owner there is the tool `tell_owner` (`{ text }`, up to 400 characters, longer refused with "shorter: one or two sentences", result "told the owner"), whose text shows as a normal agent bubble on any turn. Inbound agent messages and the chat's hidden text are quiet lines: a run of them between two visible lines folds into one muted line, "4 updates · env-proxy-cutover, tidy instagram api and 1 more" (`collapseUpdates`, `updatesLabel`; up to three senders in the order they wrote), that opens the reader with the list, each entry with its sender, time and whole text, the chat's own hidden text labeled "VP notes". Job notices and background completions themselves produce no line. The server's own steers, `[check-in] ` and `[job] ` user messages (`serverNote`), show as quiet entries from "check-in" and "jobs" and start an agent turn, not an owner turn. Sender names are display names: `child:<name>` is the job's name, a session name stays, a raw session id resolves through the catalog rows and reads "another thread" when nothing lists it. The typing dots show only on an owner turn.
- Build: a chat session loads the extension once and keeps running it, so after a service restart with new code it would still run the old tools and brief. `extensionBuild()` hashes `extension/index.ts`, `src/chats.ts`, `src/shared/chat-board.ts` and `src/shared/chat-feed.ts`; `<data dir>/extension-loads.json` records the build each chat last loaded (set at create, dropped at archive). Whenever a chat attaches (service start through `Chats.adopt` and the pin, a resume, an undo), a chat whose record differs is sent the daemon `reload` command, at once if it is idle, else at its next `agent_end` (`reloadAction`); the record then matches, so a plain restart reloads nothing.
- Board: each chat has one board file, `<data dir>/boards/<sessionId>.json` (`ChatBoard` v2 in `src/shared/types.ts`): the plan (a nested checklist of goals and steps, statuses `todo`, `doing`, `done`, `blocked`, `dropped`, each step linked to its job by name), the owner's todo list (asks to the owner: a decision, a login, an approval; each may offer 2 to 4 `choices` of up to 80 characters, the agent's recommendation first; the owner taps a choice, checks, edits or answers it), and the scratchpad, up to 200 notes nested to any depth (`ScratchItem { id, text, links, at, children }`, up to 5 links each). The plan nests to any depth and holds up to 500 items; a `plan_add` under a done goal sets that goal and every done goal above it back to `todo`, and the summary says so. A step may carry `waitUntil` (an ISO date-time, stored as UTC `toISOString`) and `waitFor` (a short text naming the event, up to 200 characters); `plan_set`, `plan_add` and `plan_update` set them, null clears them, and the check-in leaves such a step alone while it waits (see Check-in). Two writers, one path: the agent's `chat_board` tool (`{ ops }`; no ops reads the board; the result is the summaries plus the whole board as text, opening with the reply rule and then `This chat: thread:<sessionId>` so the agent can link to its own thread) and the owner's `POST api/threads/:id/board`. Both apply ops through the pure reducer `applyBoardOp` (`src/shared/chat-board.ts`) under the locked-json lock (`src/chat-board-store.ts`), all ops of a call or none; `rev` rises by one per op, ids are `p1`, `t1`, `s1`, .... Ops: `plan_set`, `plan_add`, `plan_update`, `plan_remove`, `scratch_add`, `scratch_update`, `scratch_remove`, `todo_add`, `todo_update`, `todo_remove`. The owner may use the todo and scratch ops; the plan is the agent's. The agent may hold at most 3 open todos of its own; a fourth `todo_add` is refused with "The owner already has 3 open asks. Decide this yourself and note it in the scratchpad, or remove an ask first." The agent's `todo_add`, or a `todo_update` that renames a todo, is refused when the todo has no choices and only holds a place for something not ready (`placeholderTodo`: the text starts with "Read:", or says "lands here", "link lands", "when ready", "when it's ready" or "when it is ready"; owner 10-09, correction c14): the error tells the chat to track it as a plan step and send the link in a chat message when it exists. Chat health counts the open ones as `placeholder_todos`. A v1 file (one `scratchpad` string) reads as v2 through `migrateBoard`, one note per non-empty line; a v2 file whose notes have no `children` reads with `children: []`; either is written in the current shape at its next op. The extension finds the directory from the `agent-chat-data-dir` flag, else `<agentDir>/browser-chat`, the same as the server. The server reads the board into a chat's thread snapshot (`board`, null before the first op) and watches the boards directory: a change from either writer reaches the open thread's listeners as a `{ type: "board" }` event. After an owner change the server sends the chat a steer whose text starts with `[board] ` and says what the owner did (`[board] Owner chose "Wait for QA" for "Deploy now?"`, `[board] Owner added a note: "Read this first" with links [report](file:/Users/me/r.md)`); the client shows such a message as a small owner-action line.
- Artifact links: a link is `{ label, target }`, and `target` is one of `job:<name>` (that job's latest report in this chat), `thread:<sessionId>` or `thread:<sessionId>@<timestamp ms>` (a thread, or one message in it), `wiki:<path>` (an llm-wiki page, read through `GET api/wiki-page`), `file:<absolute path>` (a text file, read through `GET api/local-file`), or an `http(s)` URL. `normalizeArtifactTarget` (`src/shared/artifact-link.ts`) stores pasted text in that form: a chat URL ending in `#<sessionId>@<ms>` or `#<sessionId>` becomes `thread:`, a wiki page URL becomes `wiki:`, a bare absolute path becomes `file:`; the reducer refuses anything else.
- Permalinks: the page hash `#<sessionId>@<timestamp>` opens that thread, chat or plain, and scrolls to the message whose `timestamp` it is, highlighted for 2 s; with no exact match it lands on the nearest message in time, so a link copied in a job drawer (the chat's receipt time) finds the job's own reply. A link to one reply is that hash, or `thread:<sessionId>@<timestamp>` on the board. Copy link sits on hover (long press on a phone) beside every bubble and job line of a chat, every prompt and reply of a thread, and every message in a job drawer, where it points into the job's own thread.
- Board panel: three cards, Plan, For you and Notes, each folding from its header; Plan and Notes keep the fold in the browser (`chat.boardCards`), For you opens whenever an ask is open. Plan steps and notes are trees: every item with children starts folded (`chat.boardItemsOpen` keeps what the owner unfolded, per chat), each shows an id chip (its board id in mono with a dot colored by a hash of the chat and item ids; a click copies the id), and a parent shows "n of m done". Done and dropped steps are hidden; a "Show done (n)" toggle per parent (and one for the top level, `chat.boardShowDone`, per chat) reveals them; the Plan header counts "n of m done" over the whole plan, and a goal reads as done only when the chat marked it done. An ask shows its choices as buttons, the first marked recommended; one tap, or Enter in the reply field that "Reply…" opens, saves the reply and checks the ask, and answered asks sit behind "Done (N)". Notes carry link chips (job, message, wiki, file, web); a chip opens the reader, the thread, or a new tab. "Add a note" offers to attach a pasted link or path as a chip; a note's + puts the next note under it, its x removes it with the notes under it. On a wide window the panel's left edge (a grip, brighter on hover) drags it between 280 px and 60% of the window (double-click puts it back to 320, Left and Right nudge it, `chat.boardWidth` keeps it); below 900 px it is the Board tab. Each row reads as one paragraph: fold, status mark and id chip sit inline before the text and a wrapped line comes back to the row's left edge; blocked is a muted ring with a slash, done a muted check. A step with an owner (`job`) has no pill: its text is the link, opening the job drawer for a subagent of the chat and the thread for a session. The chat's jobs live in the sidebar under its row (the chevron on a chat row): status, name, activity and age, running first, including the sessions it started with `rlm.create_session` once the chat is open; a job row opens its drawer in the chat.
- Plan view: an "Open plan" button on the Plan and Notes card headers (`PlanView.svelte`, `store.planView`) opens the whole board in one modal (min(1100px, 94vw) by 88vh, full screen on a phone, Esc closes): the plan as a tree with every level open, each step with its status mark, id chip, owner chip (opens the job drawer or the owner's thread) and note; then the notes tree with its link chips. Done and dropped steps hide until "Show done (n)" is on; "Collapse all" / "Expand all" folds every parent. A double click on a board panel row, its hover "open" button, or a mention chip opens the view on that item: its parents unfold, done items show when it is one, and the row scrolls into view and lights up for 2 s (`focusPlan` in `src/client/board.ts`). The view follows the board live.
- Reader: every artifact opens in one modal (`Reader.svelte`, `store.reader`, min(960px, 92vw) by 86vh, full screen on a phone), from a note chip, a job line in the feed, a message in the job drawer, or a link inside a rendered reply. `store.openArtifact(target, thread)` decides through `readerAction` (`src/client/reader.ts`): an `http(s)` URL opens a new tab, a bare `thread:<id>` opens the thread, everything else the reader. `job:<name>` shows the job's latest message to the chat in full with its earlier messages behind a fold and "Open full thread"; when that message names a wiki page (`reportWikiPage`: a `http://localhost:5176/page/<path>` URL, a `wiki:<path>` target, or an `apps/llm-wiki/content/<path>` path ending in `.html` or `.md`), the page is drawn under the report in a "Full report: <title>" section with "Open report" (a new tab on the wiki); the preview card names the same page on a "Full report: <title>" line; `file:<path>` shows markdown rendered, a `.diff` or `.patch` with line colors, anything else as code with line numbers; `wiki:<path>` shows the page itself with "Open in wiki": a `.html` page's own HTML in a sandboxed `render` frame (the frame's allowlist keeps document markup, draws `<pre class="mermaid">` blocks with mermaid, asks the chat for the page's file images by postMessage and hands link clicks back, so a link to another wiki page opens in the reader and any other link in a tab), a `.md` page rendered as a reply is; `thread:<id>@<ms>` shows that one message with "Go to message". The header carries the source and "Copy link", which copies a form the Add a note field turns back into the same link (the page URL with the message hash, the file path, the wiki URL). The job drawer keeps the job's status, brief and a one-line preview per message; each preview and "Read report" open the reader.
- Replies: an agent bubble renders markdown the way a thread reply does (lists, inline code, code blocks with Copy, bold, tables in a scroll box, links, images, mermaid), with tight bubble spacing and headings as bold lines. A board id written as a whole word (`p7`, `s3`) that is on the chat's board becomes a mention chip (the item's dot color and id, its first 60 characters on hover) in agent and owner bubbles and in the reader's update lists, inside lists, tables and bold too; an id inside a code span, a code block or a link, or one the board does not have, stays text (`mentions` extension in `src/client/markdown.ts`, keyed on the board rev in the render cache). A chip opens the plan view on that item. A web link opens a new tab; a link whose target is an artifact (`job:`, `thread:`, `wiki:`, `file:`, a bare absolute path, or a chat permalink URL) opens the reader or the thread. An image or a mermaid fence that stands as a block of its own (`bubbleBlocks` in `src/client/markdown.ts`) becomes a wide card under the bubble, up to the feed width, several stacking; one inside a sentence or list stays inline. A diagram card draws once its fence closes, also while the reply streams. The owner's own bubble renders links, inline code, bold and line breaks only.
- Guard: in a marked root the extension blocks the `edit` tool, write-mode `open(...)`, `edit(` in ipython cells, and every shell command except quick look-ups: a command (the `bash` tool, a `bash(` literal, a `!` line) passes only when it starts with `prime-agent`, `git log`, `git status`, `git diff`, `git show`, `rg`, `ls`, `cat`, `head`, `tail` or `wc` as a whole word and has no `;`, `&`, `|`, `<`, `>`, backtick, `$(` or newline outside quotes. A computed `bash(` command and `%%bash`, `%%sh`, `%%zsh` and `%%shell` cells are blocked. Calls are found with string literals and comments blanked, so a job brief that mentions `bash(` passes. `rlm.spawn` and `rlm.create_session` are allowed. Any error fails open.
- Sends: every message to a chat is a steer (`POST api/threads/:id/prompt` ignores `mode`), and the server sets steering mode `all` on every attach, so consecutive job reports batch into one turn. Stop sends `resume_queue` right after the native abort, because an abort suspends the session's input pump and an agent message to an idle suspended session is refused until then.
- Residency: chats are pinned (`ThreadHub.pin`, up to the live limit of 8): never swept or evicted, resumed again on each catalog update that finds them not live. These resumes are background attaches (`AttachQueue`): at most 2 attach at a time (`BACKGROUND_ATTACHES`), in pin order, while a tab opening a thread or an owner send attaches at once and promotes a chat still waiting; stall checks (`view`) and the Slack bridge also attach in the background. A failed resume (a daemon timeout) is tried again after 15 s, doubling per failure up to 5 min. A session the daemon lists as active but does not hold (`Unknown active session`) opens saved; a job wake that finds its thread gone (that answer, or not in the catalog) logs one line and skips it until it shows new activity. At service start every chat in the index is pinned again; one the daemon lists as archived or not at all is forgotten, with a log line. At start and every 10 minutes (`ADOPT_SCAN_MS`) `Chats.rescan` reads the head of each unarchived thread active in the last 7 days that is not in the index; one whose session file has the `chat_mode` entry (it precedes the first message, so the read stops there) is restored as a chat and logged (`re-adopted`). A thread with messages found plain is not read again. This brings back a chat unarchived outside this server, as chat-6394 was (archived 2026-10-07 15:18 UTC, unarchived 15:23, then 0 check-ins).
- Check-in: the server, not the model, checks every 15 minutes by default (`CHECK_IN_MS`, each chat can change it, `src/chat-checkin.ts`). For each chat it lists the jobs: its direct subagents (the thread's `rlm_child_update` events and snapshots, with `repliedSinceTask` and `lastActivityAt`) and every thread an open plan step names as its owner (the catalog rows, with status, last activity and message count). A step's owner is its `job` (a child name or id, a session name or id, or `thread:<id>`; the board reducer stores `thread:<id>`, `thread:<id>@<ms>`, a pasted chat URL and `job:<name>` in the bare form), else the first `thread:<id>` link in its note. The chat's own steps (its session id or name as owner) are no job and list as `owner you`. A cancelled subagent ended (no line); only an error is a failure. It skips a chat with no job at work, no open plan step (todo, doing, blocked), no board read error and no more than 3 open owner asks. Otherwise `checkInDigest` compares with the last tick's memory (`<data dir>/check-ins.json`) and keeps only what needs the VP: a subagent that finished or failed since then ("with no report" when the daemon says it did not reply and the chat's transcript holds no message from it since its last wake, and the plan item's status when the board still says todo or doing), a subagent whose last message since its wake says it waits (a slot, a go, a review) as `pN (job x) waits: "<first 60 characters>"` once per message instead of "finished", a linked thread that failed or posted new messages (going idle alone is no line), a job with no activity for 30 minutes (once per quiet stretch), a failed owner of an open step again 5, 10, then every 20 minutes (`RETRY_BACKOFF_MS`, "is still stopped: its last turn failed 15 min ago: 429"), a board the server cannot read ("the board cannot be read: <error>; call chat_board again", the step memory kept) and more than 3 open agent todos ("9 open owner todos; keep 3: decide or remove the rest"), each once per change and again every 2 hours, an agent todo the owner answered, and a plan step that can start (status todo, no job, every earlier step under the same open goal done or dropped). Every open leaf step (an open item with no open child; a goal once no step below it is open) gets one class at every tick (`stepClass`): `live` (its owner is a job at work, a thread active in the last 2 hours, or the chat itself on a step it changed in that time), `foryou` (an open agent todo names the step or shares a distinctive word with it, `todoForStep`), `waiting` (`waitUntil` still ahead, or `waitFor` or a thread owner with progress in the last 2 hours), `due` (`waitUntil` passed and the step has not changed since), `stale-chase` (it waits on another thread or an event with no progress for 2 hours, `STEP_STALE_MS`) or `orphan` (no live owner, no todo, no wait). Each `due`, `stale-chase` and `orphan` step gives its line at every tick until the chat acts (`classLine`): `pN "..." is due since 10:00: act on it or set a new waitUntil`, `pN "..." waits for "Promote 5" for 20 h: chase it now; after 24 h make it a For you todo or replan` (from 24 hours, `CHASE_ESCALATE_MS`: `make it a For you todo or replan it now`), `pN "..." has no live owner: start a job, take it yourself, or ask the owner in For you`. These class lines go after every other line, since the open-steps list repeats each class. A stale chase whose `waitFor` names a thread (`waitTarget`: `thread:<id>`, a session id, or a session name of 6 characters or more as whole words, never the chat itself or an archived thread), or whose owner is a thread, also gets a steer from the server to that thread, at most every 2 hours per step (`NUDGE_EVERY_MS`, kept in the step memory): `[from <chat>] your step pN "..." (it waits for "...") has waited 20 h: what is left, and when?`, with the `agent_message` call to answer. A step whose job (a subagent) ended or replied after the step's last change or note edit and is still unchanged at the next tick gets `Job <name> ended at HH:MM, report: <first 160 characters>` written at the top of its note through the board store (`writeBoard`), once per end, with a line telling the chat to update the step. The same classes, from the boards, the check-in memory and `prime-agent sessions --json`, are printed per chat by `node --import tsx scripts/duties/board-classes.ts`. The check-in is each chat's one built-in duty (`CHECK_IN_DUTY`, id `checkin`, correction c15): every check-in tick that runs its classes and every job event (`job-ended`, `job-waiting`, `job-stopped`) is recorded as a run of it in `<data dir>/duties/<chat>.runs.jsonl` (`Duties.recordCheckIn`; a quiet tick with the same metrics at most hourly), with six targets of 0 measured from the same classes (`convergenceMisses`: `orphan_steps`; `due_late`, a step due for longer than the chat's check-in interval; `stale_chase_24h`; `job_end_unrecorded`, a step whose job ended longer than one interval ago and after the step last changed; `job_end_silent`, the same for a job end the server told as a bad end with no report, counted there and not again in `job_end_unrecorded`; `scope_misses`, an open step on another thread's work), its step counts per class and its flagged steps. The check-in's lines act on each miss; it has no model call and no schedule of its own. Its card in Duties carries a Built-in tag, and its cadence and pause are the chat's check-in setting, the same one the header's Check-in control writes. Every duty card edits its cadence (every N minutes or a daily time) and pauses (`POST api/threads/<id>/duties` with `action: "schedule"`). After a told run (a duty's miss, or a check-in tick with lines, not one that started a check-in job), the end of the chat's turn runs the same check again once (`Duties.afterTurn`): a flagged step the chat left unchanged goes back to it by name, and the run record keeps it as `unresolved`; a step it changed is `handled`. A precheck opts in by naming the step in each flagged slice (`item`). The Chat health duty sums the six over all chats from the boards, apart from the check-ins, so a check-in that stops running still shows, and counts `unresolved_after_turn` from the after-turn records. `node --import tsx scripts/duties/remove.ts --name "<name>" [--chat <id>]` deletes a duty with its runs and saved outputs. A correction in the ledger can name a handoff (`handoff: { to, topics }`, correction c7: machine work goes to ops guy): an open step in any other chat whose text or note names a topic as whole words (`scopeMisses`; not one that says it was handed off, or whose owner or `waitFor` names the target) gets `pN "..." belongs to <to> (correction c7): hand it off with a message to that thread and remove it from this plan` when first seen and every 2 hours, and is a `scope` item for the check-in job. `node --import tsx scripts/corrections-fix.ts <id> --ref <sha> --status active` records a landed fix. A chat's schedule survives a service restart: its last check-in is read from the check-in memory at start, so restarts closer together than its interval do not keep it from ever checking in (10-09: three restarts in 16 minutes did). A due check-in that is held (an owner turn runs, or the last turn is stalled) logs `chat <id>: check-in held: <reason>` once per reason until the next digest runs. The memory keeps each plan item's last change (status, text, owner or wait; a note edit is no change, so a chase note does not hide a stall), so the first tick dates an unseen item from the board's `updatedAt`. The first tick takes the baseline and reports only conditions (a stale job, a step's class, a ready step). A check-in less than 60 s after the server's last `[check-in]` steer to that chat (a digest or a restart) waits and runs at the first scheduler wake after the 60 s, so its lines join one message (`CHECK_IN_MERGE_MS`). With any line it steers the chat once with `[check-in] What changed:` and up to six bullets, then `Open steps, oldest change first:` with every open leaf step, an open item with no open child (id, class, text, status, owner or "no owner", waits, time since its last change; at most 30); with none it sends nothing, so no model call. Separately, when a subagent ends a follow-up task (status unchanged, activity gone) and `repliedSinceTask` is false, the server steers, 90 s later if it is still quiet, `[job] <name> is waiting for you since HH:MM (last message: "...")` when the chat's transcript holds a message from it since its last wake (the message's time), else `[job] <name> ended at HH:MM with no report` (the job's last activity, local time, so two ends read as two events), once per end (two ends whose last activity is less than 60 s apart are one end, `NO_REPORT_SAME_END_MS`, unless a new message arrived). The notice records that end in the check-in memory, so the next digest does not tell it again as `waits` or `finished`. The daemon's own `rlm_child_terminal_notice` covers a first task that ends with no reply. A job (a subagent or a create_session root in the chat row's Agents list) whose last turn ended on a provider error, an abort, a stop mid-tool (a tool call or tool result the model never answered) or the output length limit, and that sent the chat no report since its last start (`repliedSinceTask`, else no message from it in the chat's transcript since its last user or agent message), is told at once, at the scheduler wake that reads it (`jobEnd`, `Chats.jobEndNote`): one steer `[check-in] What changed:` with `pN "...": Job <name> stopped on a provider error ("<first 120 characters>") at HH:MM and sent no report: re-brief it with a follow-up, restart it, or replace it` (or `was aborted`, `stopped in the middle of a tool call`, `hit the output length limit`), and the same text at the top of its open step's note through `writeBoard`. Each end is told once and kept in `check-ins.json` under `ends` (by child id or `thread:<sessionId>`, a week), so a restart does not repeat it; the check-in memory and the no-report notice see it as told. A transient failure goes to the job wake first, so a job it revives gets no note; a cancelled subagent, one the server holds no snapshot of, and an end more than 2 hours old when found (`JOB_END_NOTE_MAX_AGE_MS`) get none. Every 10 minutes per chat (`JOB_CLEANUP_EVERY_MS`) the scheduler deletes each finished job (`finishedJobs`: a direct subagent that is done, reported, quiet an hour, and owned by no open step nor named in an open step's `waitFor`) with the daemon's `delete_rlm_subagent`, once, with one log line, so its worker and Python kernel stop holding memory. The daemon check-in heartbeat of older builds is cleared on the next attach (a heartbeat whose prompt starts with `OLD_CHECK_IN`). The jobs panel shows "Check-in every 15 min, on changes only" while a job runs or a step is open. The chat can change its own check-in with the chat_board `check_in` argument (`{ pause: "1h" | "tomorrow" | null, every_minutes }`, `chatCheckIn`): it writes the owner's `<data dir>/check-in-settings.json` with the same rules (whole minutes 1 to 240, "tomorrow" is the next 09:00), never pauses until resumed, and cannot pause or resume over a pause the owner set that is still in force (`pausedBy`); whoever writes later wins otherwise, so the owner's later choice replaces the chat's. The result's first line (`The chat set its check-in: paused until 2026-10-09 09:00`) shows in the feed as a notice line. The check-in of a chat that runs an owner turn (`turnStarter`, a message or a `[board] ` action) waits and goes at the first scheduler wake after it; a turn a check-in or a job started does not hold it. A chat whose last turn ended in `error` or `aborted` (a 429, a connection error, a Stop), or whose provider retry holds input queued behind a failure, is stalled (`turnStall` in `src/chat-fallback.ts`); it gets no digest and no `[job]` notice, since a steer then waits in its queue unseen (chat-453e got 4 check-ins and 25 notices 2 h late; VP of CI sat 32 min in a 429 provider wait with 6 owner messages queued). Instead the scheduler restarts it through `ThreadHub.restart` (abort when a provider retry holds the turn, the steer, then `resume_queue`): a turn something else started gets `[check-in] Your last turn failed at HH:MM (<error>). Re-check the board and continue.` 5 minutes after the failure, then 10, then every 20; a failed owner turn (not a Stop) gets `[check-in] Your last turn failed at HH:MM (<error>). The owner's message is still unanswered: "<text>". Answer it first.` after 30 s, then 5, 10, 20 min, and that turn stays the owner's (`OWNER_RETRY_MARK`), so the answer is a bubble. While it waits, the feed shows `Turn failed (<error>). Retrying at HH:MM.` under the owner's message (the hub's `wait` event). A provider retry with nothing queued is left to the session. Never while the chat is paused. It reads `running` (a turn, compaction, command, retry or session action), not `busy`, because queued input counts as busy. The digest memory stays, so the changes are told at the first check-in after the restart. A transient failure (the pool token command failed or hit Prime's 10 s limit, `Connection error.`, fetch failed, ECONNRESET, ETIMEDOUT, socket hang up; `failureCause`) restarts after 30 s, 1 min, 2 min, then 5, 10, 20 min (`TRANSIENT_RETRY_BACKOFF_MS`), owner turns still quoting the owner. The scheduler wakes every 30 s; a gap of more than 90 s between two wakes means the Mac slept (`wokeFromSleep`), and that wake restarts every chat with a transient stall at once and starts its schedule over. Claude fallback: when a chat on an Anthropic model stalls because Claude cannot serve (no Claude account, or a 429, 401, Consumer Terms 400 or transient failure while `pi-pool ls` shows no usable Claude account, read at most once a minute by `claudeReader`; a pool that cannot be read means retry, not a switch), the server records its model and thinking level in `<data dir>/chat-fallbacks.json`, switches it to `openai-codex/gpt-6-sol` (else the closest configured Codex model), posts one notice line (`Claude has no free account; switched to GPT-6 Sol. I switch back when one frees up.`) and restarts the turn at once. Between turns, once the pool shows a usable Claude account, it switches back with one notice; a chat the owner moved off the fallback keeps the owner's model. With no Codex model the feed shows `Waiting for a Claude account until HH:MM` (the earliest limit, cooldown or window reset). A chat on a non-Anthropic model is never switched. A thread that owns an open step, whose last turn failed and that still holds queued input, gets abort, a `continue` steer and `resume_queue` at the chat's check-in, then on the 5, 10, 20 min schedule. A job of a chat that is not paused (a subagent or create_session root in the chat row's Agents list) whose last turn ended in a transient failure gets the same wake, queued input or not, once per failure, on the transient schedule and at once after a sleep (`jobWake`); the scheduler reads a job again only when its activity changed or while a failure of it waits. While any chat or job of one works, the service holds a macOS idle-sleep assertion with one `caffeinate -i -w <service pid>` child, killed 2 minutes after nothing works and at close (`src/chat-awake.ts`); lid-close sleep still happens. A model change in the header or an account change in Accounts on a stalled thread applies at once: a chat restarts its turn on the new choice, a plain thread gets its provider retry stopped and its queue resumed, so the next send is not stuck behind the old wait.
- Origin: every row carries `origin: "user" | "agent"` and the sidebar hides agent-created sessions by default. The daemon records no creator, so `src/thread-origin.ts` decides, in order: an id in `<data dir>/threads.json` (every thread `POST api/threads` created, both kinds) or in `chats.json` is `user`; else the session file decides, `agent` when its first `session_info` precedes its first `session_state` (a `create` request with a name writes the name first; `rlm.create_session` names roots at create, a person's session is renamed later), with files that have no `session_state` falling back to the name preceding the first message; else `user`. A file's decision is kept once it has a `session_state` or `message` entry. Sessions a person created with a name through a `create` request outside this server (`prime-agent --name`) read as `agent`; so do named browser threads from before `threads.json` existed.

## HTTP API

All routes sit under the capability URL. A browser navigation the person typed or bookmarked to `http://127.0.0.1:<port>/` (`Sec-Fetch-Site: none`) redirects there; every other request to `/` gets 404. Writes need JSON, the page token in `X-Chat-Token`, and the exact `Origin` for the requested host, either loopback HTTP or the configured HTTPS origin.

| Route | Purpose |
| --- | --- |
| `GET manifest.webmanifest`, `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `apple-touch-icon.png`, `favicon-32.png`, `favicon-64.png` | the installable app: web app manifest and icons (see Mac app) |
| `GET api/ws?token=` (WebSocket) | the page's one live connection: sessions, open threads and sign-in feeds (below) |

| `GET api/threads/:id/stream` | SSE snapshot, then native events |
| `GET api/threads/:id/tool-output?toolCallId=` | full tool result text |
| `GET api/threads/:id/part?message=&part=` | full text of a truncated part |
| `GET api/threads/:id/commands`, `GET api/commands` | native commands and skills, for a thread or the new-chat screen |
| `GET api/threads/:id/stats` | native session stats: token totals with cache read and write, cost |
| `GET api/models?id=` | model catalog and current model; with no id, `current` and the effort are the new-chat defaults |
| `GET api/defaults` | the model and effort a new chat starts with (Prime Agent `defaultProvider`, `defaultModel`, `defaultThinkingLevel`) |

| `GET api/workspaces` | recent working directories |

| `GET api/accounts?id=` | pool state for a thread |
| `GET api/usage/summary` | Settings > Usage headline: rolling tokens per second, minute and day for every agent on this Mac, one number per token kind (output, input, cacheRead, cacheWrite, total), the sparklines per kind, the cost today and the sync state (`UsageSummary` in `src/shared/usage.ts`) |

| `GET api/usage/models?window=` | `{ models }`: one row per source and model in the window with calls, tokens, cost and the median output tokens per second (`UsageModelRow`) |
| `GET api/images/:hash` | an image from the transcript |
| `GET api/local-file?path=` | `{ path, text, kind, language? }` of a UTF-8 text file (no NUL byte in its first 8 KiB) up to 2 MiB, read-only, whose real path is under `~/.prime/agent/session-artifacts`, `~/.prime/agent/browser-chat` or `~/Documents/Github` with no hidden part below it; the service's `configuration.json` is refused. `kind` is `markdown` for `.md`, `diff` for `.diff` and `.patch`, else `code` with `language` the extension |
| `GET api/wiki-page?path=` | `{ path, title, url, dir, kind: "html", html }` or `{ ..., kind: "markdown", text }` of an llm-wiki page, fetched by the service from `http://localhost:5176/api/agent/page` with a 5 s timeout, so a phone on the tailnet reads it too; the wiki's 404 and read-cap refusals pass through; when the wiki does not answer the page's file under `~/Documents/Github/auto-sns-agent/apps/llm-wiki/content` is read instead, and a page in neither place is 502; anything but a `.html` or `.md` page is 415 |
| `GET api/labels` | saved tags and per-thread tags, priority and progress |
| `GET api/threads/:id/child-usage` | native usage cost of each subagent of a thread |
| `POST api/threads` | create a thread and send the first message; `kind: "chat"` creates a chat; the id goes in `threads.json` |
| `POST api/threads/:id/prompt` | send, queue or steer |
| `POST api/threads/:id/board` | chats only (404 otherwise): `{ ops }` with owner todo and scratch ops, returns `{ board, sent }`, then steers the chat with a `[board] ` line |
| `POST api/threads/:id/abort`, `rename`, `model`, `thinking`, `queue`, `read`, `archive`, `unarchive` | thread controls; `unarchive` of a chat restores it as a chat |
| `POST api/warm` | attach ahead of a click |
| `POST api/accounts` | pool actions: use, follow, pin, unpin, switch, recheck, resets (read Claude reset grants), reset (spend one, `grant` optional), disable, enable, remove |
| `POST api/accounts/refresh` | read usage now for every account of `provider`, or one `account`; progress goes out on the `refresh` feed |
| `GET api/accounts/login/stream` | SSE state of the current or last sign-in |
| `POST api/accounts/login`, `login/paste`, `login/cancel` | start a sign-in (add, or again with `account`), send a pasted code, cancel |
| `POST api/labels` | `create`, `rename`, `delete` a tag; `tag` threads on or off; set `priority` 0 to 3; set `progress` |

The page opens one WebSocket, `api/ws?token=<page token>`, and carries every live feed on it. Each EventSource used one of the six HTTP/1.1 connections Chromium allows per host, so three tabs used them all and later requests queued. The upgrade needs the exact page Origin for the requested host and the page token, the same pair a POST needs. Messages are JSON text frames. The page sends `{"type":"subscribe","sub":1,"feed":"sessions"}`, `{"type":"subscribe","sub":2,"feed":"thread","id":"<thread id>"}`, `{"type":"subscribe","sub":3,"feed":"login"}`, `{"type":"subscribe","sub":4,"feed":"refresh"}` (the latest usage refresh per provider), `{"type":"subscribe","sub":5,"feed":"usage"}` (the Settings > Usage summary, once at subscribe and then about every 2 s) and `{"type":"unsubscribe","sub":2}`. The service answers `{"sub":1,"event":"build"|"sessions"|"thread"|"login"|"refresh"|"usage","data":...}`, the same payloads as the SSE events, and sends `{"event":"ping"}` with a protocol ping every 25 s. The page drops a socket that is silent for 70 s, reconnects with backoff (0.5 s doubling to 30 s), reconnects at once when the tab becomes visible or the network returns, and subscribes every feed again, so each thread gets a fresh snapshot.

## Phone access through Tailscale

The main chat instance (`~/.prime/agent/browser-chat`) opens on your other devices through Tailscale with no setup. Keep Tailscale connected on the Mac and the phone, signed in to the same tailnet. The tailnet needs MagicDNS and HTTPS Certificates turned on (DNS page of the Tailscale admin console).

```text
phone (tailnet) --https--> https://<mac>.<tailnet>.ts.net/<secret>/
                             Tailscale Serve on the Mac, port 443, path /
                               --> http://127.0.0.1:5182/<secret>/  (chat listener, loopback only)
```

- On start and every 60 s the service reads `tailscale status --json` and `tailscale serve status --json`. If `https://<mac>.<tailnet>.ts.net/` has no handler, it runs `tailscale serve --bg --https=443 http://127.0.0.1:5182`. A handler there that points anywhere else is never replaced; Settings shows the command that frees it.
- The service then requests `https://<mac>.<tailnet>.ts.net/<secret>/api/identity` from the Mac and checks that this instance answered. Settings shows the time and result of the last check.
- The phone link is `https://<mac>.<tailnet>.ts.net/<secret>/`. It stays the same across restarts. If the machine is renamed in Tailscale, the service follows the new name on its next check.
- Settings > Phone access has the link, a Copy button and a QR code. Scan it with the phone camera and bookmark the page. `sieun-pi chat status` also prints it as `Phone:`, and `/agent-chat` prints it under the local URL.
- Turning "Open from my devices on Tailscale" off removes only this chat's root handler (`tailscale serve --https=443 --set-path=/ off`) and the remote host stops working at once. The switches change only from a page opened on the Mac (`127.0.0.1`); a remote page sees them read-only.
- `chat start --public-origin tailscale|https://HOST|none` sets the same thing from the terminal while chat is stopped. An HTTPS origin is fixed and never touches Tailscale. Instances with `--data-dir`, or under a different HOME, start with phone access off. `SIEUN_PI_CHAT_AUTOMATIC=0` turns the automatic defaults off for the main instance too.

The listener stays on `127.0.0.1`. Only the current remote host is allowed, with matching HTTPS Origin and page-token checks for writes. Forwarded headers cannot add hosts. The service-stop API stays local-only. A cross-site link may open the secret chat page; cross-site API requests remain blocked. Assets and event streams use relative URLs, so they pass through the same proxy.

Keep the full URL private. Anyone who can reach the service and has that URL can read chats and control agents. Tailscale Serve limits network access to devices on the tailnet; do not use Funnel or an unauthenticated public proxy. Other HTTPS reverse proxies must preserve Host, pass WebSocket upgrades on the chat path, and restrict who can connect. Keep the Mac awake.

## Slack

The main instance can sync a chat to a Slack channel, `#vp-<chat name>` and private by default. It uses Socket Mode: one outbound WebSocket from this Mac, no public URL.
The bridge is off by default. With no tokens it stays off and the service runs as before.
Sync is opt-in per chat and off for every chat by default. "Connect to Slack" at the top right of a chat opens the setup dialog: the channel name (prefilled, checked the way Slack checks it: lowercase letters, numbers, hyphens and underscores, at most 80 characters), private or public, or an existing channel the bot is in (a list when the bot can list channels, else a field for an id or `#name`). The Slack button next to poteto-mode on the new-chat screen opens the same dialog for a chat you are about to create.
A connected chat shows the Slack mark and `#name`; clicking it opens the same dialog on the channel, with an Open in Slack link, a rename, and "Stop syncing" behind a confirm. A click never turns sync off.
Connect is idempotent: a chat that is already synced keeps its channel, a name that is taken is reused when the bot is in that channel, and repeated or concurrent connects (a double click, two tabs) make one channel because the bridge runs one chat's actions in turn.
Stop syncing archives the channel. Archiving the chat (after its confirm) archives its channel too; unarchiving the chat opens the same channel again (a new one if Slack refuses).

- In: a message you write in a chat's channel is a steer to that chat, the same call as the browser composer. An hourglass reaction stays on it until the turn ends.
- Out: the lines the browser feed shows on the left: replies on turns you started and `tell_owner` pings. Job reports and the chat's own notes stay quiet. Messages you type in the browser are not copied to Slack.
- Only your member id, in the team the bot token belongs to, is accepted. Bot posts, edits and deletes are dropped.
- Each line is posted once, keyed by message timestamp plus `toolCallId`, so compaction does not repost. Lines from before a chat was linked are never posted.
- After a reconnect (the Mac slept) the bridge reads each channel with `conversations.history` since the last handled message, because Socket Mode does not replay missed events.
- State lives in `<data dir>/slack.json`: the workspace connection and one link per synced chat (`channelName`, `isPrivate`, `archived` while the chat is archived).
- Public channels need the `channels:manage`, `channels:read`, `channels:history` scopes and the `message.channels` event from the manifest; an app installed before 2026-10-09 has to be reinstalled from the manifest for them.
- A synced chat whose feed does not open (its session is gone) is parked: one log line, then a quiet retry after 1 minute, doubling up to 30 minutes, so a dead session costs no daemon attach on every catalog update.
- Sync became opt-in on 2026-10-08. At the first connect after that, the bridge unlinked and archived every channel it had linked before, except `#vp-slack-bridge-probe`, and recorded `opt-in-2026-10-08` under `migrations` in slack.json so it never runs again.
- Text only for now: files you attach in Slack are not forwarded.

Setup: create the app from [`slack-app-manifest.yaml`](slack-app-manifest.yaml) (the file lists the steps), install it, and add an app-level token with `connections:write`.
Save both tokens in the Keychain, never in the repository:

```sh
security add-generic-password -U -s sieun-pi-slack -a bot-token -w   # xoxb-
security add-generic-password -U -s sieun-pi-slack -a app-token -w   # xapp-
```

`SIEUN_PI_SLACK_BOT_TOKEN` and `SIEUN_PI_SLACK_APP_TOKEN` work instead, for example through `dotenvx run -- sieun-pi chat serve`.
Then open Settings > Slack on the Mac, enter your member id and turn on "Connect Slack". Then press "Connect to Slack" in each chat you want in Slack. The refresh button reads the tokens again without a restart.
Only the main instance runs the bridge, so a test instance never opens a second Socket Mode connection; `SIEUN_PI_SLACK=1` or `0` overrides that.
Anyone who can post as your Slack account can drive agents with full access to this Mac, and workspace admins can read the channels. Use 2FA on that account.

## Keep running

On macOS the main instance runs as the LaunchAgent `com.sieun.agent-chat` (`~/Library/LaunchAgents/com.sieun.agent-chat.plist`). The first `chat start` or `/agent-chat` writes and loads it, so there is nothing to install by hand.

- At login launchd starts `chat serve --supervised`. After a crash it restarts it within about 10 s. `chat stop` exits cleanly, so launchd leaves it stopped until `chat start`, `/agent-chat` or the next login.
- If another chat process already holds the port, the supervised process waits for it. It takes over when that process crashes and stays idle when it stops with `chat stop`.
- Settings > Phone access > "Keep the chat running" turns this off. That removes the plist; a process that launchd started keeps running until it stops.
- Output goes to `~/.prime/agent/browser-chat/service.log`.
- The chat keeps the Prime Agent daemon running (`src/chat-daemon.ts`). Nothing else starts the daemon at login, so without this the chat came up after a reboot with no daemon until a terminal ran `prime-agent`. When the socket does not answer, the chat starts the daemon the way the official CLI does when a command finds none: the installed launcher `${PRIME_AGENT_INSTALL_DIR:-${XDG_DATA_HOME:-~/.local/share}/prime-agent}/bin/prime-agent` (the link the installer moves to each new release, so an update is followed with no path in the chat), else `prime-agent` on PATH, run as `--mode daemon --daemon-socket <socket>`, detached in its own process group, from the home folder. It then waits up to 30 s for the socket.
- The daemon gets the variables an interactive login shell exports (`$SHELL -i -l -c 'env -0'`, 15 s limit), the same ones a terminal would give it: launchd starts the chat with a bare PATH and none of the tokens the shell startup files export. A shell that fails or hangs falls back to the chat's own variables and the log line says so. Daemon-internal variables (`PRIME_AGENT_INTERNAL_*`) are dropped, as the official launcher drops them.
- One daemon per socket: the chat never starts one while the socket answers, and the daemon itself holds the `<socket>.lock` lease (refreshed every second, stale after 5 s) and refuses a socket in use. Two starters that race leave one daemon; the loser exits after it waits for the lease. A socket and lock left by a power-off are taken over after 5 s.
- A failed start is tried again after 2, 4, 8, 16, 32 s and then every 60 s. The chat also holds one connection to the daemon; when it closes (a crash, `prime-agent shutdown`), the chat checks again after 3 s and starts the daemon if nothing answers. Each attempt and each lost connection writes one line to `service.log`. The daemon outlives the chat: stopping or restarting the chat, or launchd stopping its job, leaves it running.
- Only the main instance does this. `SIEUN_PI_CHAT_START_DAEMON=1` turns it on for another instance (the native test does), `0` turns it off. `chat status` prints whether the daemon answers.

## Mac app

The chat installs as an app from Chrome or Aside with no native build: its own window and a Dock icon that survive reboots.

- The page links `manifest.webmanifest` (`appManifest` in `src/chat-assets.ts`): name "Prime Agent chat", `display: standalone`, and `id`, `start_url` and `scope` all `./`, so the app opens the capability URL it was installed from and one capability is one app. The icons (a white four-point spark on a violet tile) are drawn in code by `src/chat-icon.ts` on first request: 192 and 512 px on the macOS icon grid, a full-bleed 512 px maskable icon, a 180 px Apple touch icon for a phone home screen, and 32 and 64 px favicons drawn edge to edge for the tab. The page policy adds only `manifest-src 'self'`.
- Install: open the chat on this Mac, then use the browser menu (Install page as app, or the install icon in the address bar). Remove it from the app window's menu.
- `sieun-pi open` (the same as `sieun-pi chat open`) starts the chat if needed (the login item for the main instance), then opens the installed app window, else the URL in the default browser. It finds the app by the start URL that Chromium writes into the app bundle (`CrAppModeShortcutURL` in `~/Applications/<Browser> Apps.localized/<App>.app/Contents/Info.plist`), so it needs no Prime Agent session and works for whichever browser installed it.
- Settings > Phone access > "Open the app at login" (on by default, `openAppAtLogin` in the chat configuration) opens the installed app window once after each login. The first `chat serve --supervised` of a boot waits until its own `api/identity` answers, then runs `/usr/bin/open` on the app bundle. It keeps the boot time (`sysctl kern.boottime`) in `<data dir>/login-window.json`, so a crash restart, an exit-75 update restart or `chat start` later in the same boot opens nothing. Two readings within 10 s count as one boot, because macOS moves `kern.boottime` when it corrects the clock. That first start decides for the whole boot: a switch turned on later opens the window at the next login. With no installed app it opens nothing, no browser tab either, and writes one line to `service.log`. The note under the switch says what the next login does: "Opens <app> once after each login", or "Install the chat as an app from Chrome first". It needs "Keep the chat running", changes only from a page on `127.0.0.1` like the other switches, and exists only on the main instance; `SIEUN_PI_CHAT_OPEN_AT_LOGIN=1` gives another instance the switch and makes its `serve` act as a login start, `0` turns it off.
- After a reboot: launchd starts the chat at login, the chat starts the daemon, and once the chat answers it opens the app window at the same URL (the bullet above). With that switch off, open the app from the Dock or with `sieun-pi open`. A window the browser restored before the chat answered shows the browser's connection error; reload it with Cmd+R.

## Limits

- Message text up to 32,000 characters. Up to 4 images per message, 3 MiB each, 8 MiB total, PNG, JPEG, GIF or WebP.
- Extension commands that need terminal dialogs are refused with a message. Prompt and skill commands work.
- The image store is in memory and bounded, so an image URL can expire after a restart. Reopen the thread to refresh it.
