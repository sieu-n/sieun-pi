# Browser chat for Prime Agent

A thin browser front end for native Prime Agent sessions. `/what-did-i-say` and `/agent-chat` in the terminal start or reuse the shared server and print its URL. Nothing opens a browser for you, except `sieun-pi open` (see Mac app). Run `/reload` in the terminal after updating the extension.

Prime Agent owns every run, queue, name, model, skill and worker. The browser attaches to the daemon the same way the terminal's agents view does. Closing or refreshing a tab never stops a worker.

## What you see

- Sidebar: one list. A thread with an active or paused heartbeat or cron job (daemon `cron_list`) sits in the Heartbeats section at the top, above Needs response, in the same order as the other sections. A click on the Heartbeats label folds the section; a folded section shows a dot when a heartbeat needs a response, and the browser keeps the choice. The top row holds the search box (thread titles and tag names), three view icons and the Filter button. The list icon shows each card in full; the tag icon keeps the same threads, sections and order but shows only the tag chips on the second line (a card with no tag is one line); the chat icon shows Chats only, the chat rows without heartbeats and plain threads. When the rows run on more than one box, a row of machine buttons under the search box (All, then each hosts.json name from the rows' `host`) shows one box's rows with one click. The threads below Heartbeats sort Needs response first, then Working (the daemon `rosterStatus` is running, the same Running section as the terminal agents view; a thread whose only work is running subagents is idle there too), then the rest by priority and recent activity, or, with the Chronological sort, as one list by recent activity. The Filter button opens the Agents view filters (status, tag, priority, workspace, model) for the sidebar list and the sort choice; the button shows how many filters are on, and Clear resets them. View, machine, filter and sort are saved in the browser. Needs response means the thread is not running, has messages, and had activity after you last read it in the browser. A thread you open keeps its Needs response place while it stays open and the tab is visible; it counts as read when you open another thread or the tab goes hidden. Each card has two lines. The first is the title with a spinner while it works or a dot when it needs a response. The second is the age ("3d", "2mo", nothing for a thread created today; or the heartbeat label and next run), the session cost from the native session usage ("$0.00" when zero, a dash when the daemon reports none), a short model name ("opus-5.5", "astra-6"), tag chips and a priority mark of 0 to 3 bars. Hover a card for its actions: add a tag, archive, and the menu (rename, priority, tags, archive). Right click or Shift+F10 opens the same menu. Archive works like Ctrl+X in the terminal agents view, for any thread: one click kills the resident session ("Unknown active session" counts as done), records the native archived state in the session file, and drops the server's own attachment. The row leaves the list at once (the server holds it as archived until the daemon list agrees), an open thread hands the view to the next thread in the sidebar or New chat, and a toast offers Undo for 6 seconds, which records the session as active again (it comes back as a saved thread that resumes on reply). Archived threads sit behind a toggle. Drag the right edge to set a width from 180 to 480 px; drag it under 120 px and the sidebar snaps closed, the same state as Cmd+B. A click or drag on the closed edge opens it again at the last width. The edge also takes Left/Right, Home/End and Enter. The width is saved in the browser.
- Freshness: a running thread's mark comes from the native daemon summary the sessions stream already carries (no extra polling): `lastActivityAt` of the thread or of its freshest running subagent, the one-line `summary`, `lastHeardFromAt` and the failed worker state. Live (activity in the last 60 s) keeps the spinner; quiet (1 to 5 min) dims it and shows "quiet 3m"; stalled (5 min or more, or the worker went silent) shows an amber dot and "no activity 41m"; failed (the worker failed, or the daemon summary reports a failing model call such as "Model request failed", a usage or rate limit, "Try again in" or a retry, and the daemon judged that line at the thread's present message count, which it signals by sending `taskState`) shows a red dot and that line on row two, full text on hover. The daemon writes the failure line when a session settles idle on an assistant error and keeps it until its recap model replaces it, so a thread that ran on past the failure still carries the old line; without `taskState` the line is stale and the activity marks decide. The thresholds: a model call or tool streams events every few seconds, so a silent minute is unusual and five silent minutes means the run is stuck. Waiting (the run waits before its next model call, so its quiet is expected) shows the amber dot and "waiting for a turn, place 3 of 7" or "waiting for an account until 15:42" in place of the quiet or stalled text, in the sidebar, the Agents view, the subagent rows, the job drawer, the thread's status line and its live work row. It comes from Prime's own `waitingFor` label on the daemon row when Prime sends one, else from the turn queue the catalog already reads (`queueSource`), else, for a run asleep in Prime's provider retry, from the account wait `pi-pool who` names for its tree (`treeAccountWaits`, answered from the shared pool reader's last reading). The Agents view has a Stalled status filter and the same marks; the Subagents button adds an amber or red dot when a running child is stalled or failing, and each child row shows the same mark and text. In an open thread, the live work row's hover title shows how long the current tool call has run and when its last event arrived; after a silent minute the row shows "quiet 1m" in faint text, and "no event for 6m" in amber past 5 minutes. The line under the composer shows only what the work row does not: compacting, a retry, a shell command the user started, or queued messages. A thread that is not running but settled on a failed model call (the daemon sends task state "error" with the line) shows a red dot and the failure line in place of row two until a later message replaces it.
- Tags: one tag picker everywhere (the card, the thread header, the menu, and the Agents bulk bar). Type to filter. Enter creates the typed tag and assigns it, or toggles the highlighted one. Assigned tags show as chips on top; a click on a chip, or Backspace in the empty field, removes one. In the thread header a click on a tag chip removes it.
- Agents view: the list button at the top of the sidebar, or Cmd+K, opens a full-screen table of every thread. Cmd+K again or Esc closes it. The header row holds search, filter menus (status, tag, priority, workspace, model, and machine when the rows run on more than one box) whose options show their real marks (tag chips in their color, priority bars, status dots), a created date range with presets and a month grid, the Archived toggle and a Columns menu. Workspace and Created are hidden by default; Columns turns any optional column on or off and the browser keeps the choice. Titles are 14 px, and a second line under the title shows a failure, what a running thread is doing, or a heartbeat's schedule. Every column sorts, including cost. A bulk bar sets tags, priority and archive. A click on a row's Tags or Priority cell opens the same picker as the sidebar for that row. Archived threads are hidden until you press Archived. Up and Down move, Enter opens, Space selects, Cmd+A selects all.
- New chat: the default screen. A greeting, an optional thread name field (Enter moves to the composer) and the composer, which holds only the input and the send button. The row under the box holds the workspace (recent folders, a path field that takes `~/` or `/` and checks that the folder exists, and Choose path, which opens the macOS folder dialog when the page is on 127.0.0.1), the account and the model and effort on the left (a click on the account opens the pool accounts for the selected model's provider: Follow the pool by default with its next pick named, each account with plan, usage meters and state; accounts that cannot serve are greyed and need a second click; another provider's model resets the choice), and Tags and Priority on the right, which set labels for the new thread with the same pickers as the sidebar (the tag picker can create a tag). The row wraps on a narrow window. The first send creates a resident native session with the chosen model and effort, runs `pi-pool use <account> --session <id>` when an account was chosen (a failed use sends nothing and keeps the draft), sets the thread name when one was typed, then prompts, so the first model request already uses that account and the sidebar never shows the first message as the title. It attaches, streams the reply, and then writes the chosen labels to the new thread.
- Thread: the whole transcript, opened at the bottom. Only what the user typed is a bubble on the right; a skill invocation shows the typed text with a skill tag. Agent messages, heartbeats and background command completions show as one muted line that also holds the turn's work. The header is one 40 px row: the title (click to rename: the field starts with the current title selected, Enter saves, Esc or a click elsewhere cancels, an unchanged or empty name sends nothing), the workspace, the tags with an add button, Priority (the bars mark, with the value as text when the window is 900 px or wider; a click opens the same picker as the sidebar and saves at once), the subagents button and Archive. Each turn shows the prompt, or a one-line trigger, and only its final reply. Messages that wake the agent after that reply (agent messages, background completions, subagent exits and failures, goal continuations, restart notices) never take the prompt's reply away. They fold into one row under it, "28 messages after this reply"; in the thread's last turn the newest one stays open with its reply, under "9 earlier messages". A model call that fails with no text after a reply keeps the reply and shows the error under it. Everything else in the turn (thinking, tool calls, interim messages, system notes, agent messages that arrived mid-run) folds into one collapsed row such as "Worked 6m 12s · 39 tool calls · 3 notes". While the turn runs, that row is one quiet line: a spinner, the current verb ("Running ipython", "Thinking", "Writing") with a light shimmer, the elapsed time and the tool's arguments in small mono; it stays collapsed until you open it. Open, the work is a timeline with a thin left rule: thinking in small muted text with a fade and a "more" button, and one row per tool call with its name, arguments, duration, and a red x only on a failure. Replies render as markdown with copy buttons. Web links (`http`, `https`, `mailto`) open in a new tab with no referrer; file paths and other link targets show as mono text with the target on hover. Tables sit in a bordered box that scrolls sideways when wide. Markdown images show inline and open large on a click: `https` and `data:` images as they are, and files on this Mac (an absolute path, `~/`, `file://`, or a path relative to the thread folder) through `api/local-image`, which serves only PNG, JPEG, GIF, WebP and SVG files up to 25 MiB whose bytes match the type. A missing file shows as "Image not found: <path>". A ```` ```mermaid ```` block draws after the reply stops streaming and when it comes near the screen, in a sandboxed frame (see Diagrams below); a Diagram / Source switch and Expand, which opens it in a large dialog, appear once it has drawn, and a block that fails to draw shows its source with the error. Errors and stopped replies stay visible. When you scroll up, "Jump to latest" floats just above the composer and moves up as the draft grows; its x hides it until you are back at the bottom.
- Subagents: the header button shows a spinner and "2 of 9" while any child runs, else the child count. It opens a list grouped Running, Failed, Done and Cancelled, with a filter box and an All / Running / Finished switch. Each row has the status, name, short model name, cost and run time, and a second line: for a running child its native activity ("Running bash", "Thinking", "Writing") and latest recap; for a finished one its answer preview, the error line, or Cancelled. A click opens the child's own transcript when the daemon lists its session. Rows render in a window, so hundreds of children stay fast. Cost and the session id come from the child sessions in the daemon list (matched by `rlmChildId`); the child snapshot carries status, activity, recap, error, answer preview, model and `durationMs`, but no start or finish time. Over 40 children the list opens in a dialog.
- Composer: Enter sends, Shift+Enter adds a line, images paste or drop in. A "/" at the start of the text, or after a space or a new line, opens the native command and skill menu for the word at the caret (a slash inside a word or a URL does not); picking a command replaces only that word and keeps the rest of the text. Only a command at the very start of the message runs as a command or expands a skill; a `/skill:name` later in the text is sent as plain text. The menu matches a skill with or without its `skill:` prefix and by description, and it works on the new-chat screen too. It lists the native session commands `/compact`, `/refine`, `/goal` and `/autonomous`; they run through the normal prompt path. While the agent works, Send becomes Steer and a Stop button appears. Only while the agent works, the arrow next to Send chooses what Enter does: Steer (the default) or Queue. Cmd+Enter does the other one. The choice is saved in the browser. Queued messages show as chips you can edit or remove.
- Model button: a search box (Enter picks the highlighted model, arrows move), Favorites (GPT-6 Astra, Claude Opus 5.5 and Claude Fable 5.1 by default; the star adds or removes one, saved in the browser), the other models by provider, and an Effort row with the model's native thinking levels. On a thread, native `setModel` and `setThinkingLevel` also set the default for new chats. Menus open as top-layer panels that flip above or below to stay on screen.
- Context: hover or focus the ring to see context tokens, session cost, input, output, cache read and cache write totals from native `getSessionStats`, and the last call's cache hit rate from its native `usage`. A dot flags a cache problem: red when a warm call (same model, under 5 minutes after the previous call, prompt of 10k tokens or more) reads under 50% from the cache; amber when it reads under 90%, or 10 points under the thread's median, when it writes more than 20% of its prompt to the cache, or when 2 of the last 20 warm calls missed. The thresholds come from 13,583 warm calls in 40 recent threads (median hit 99.5%, p5 93.9%).
- Prompt: the layers icon in a thread or chat header, a job drawer, a duty run or the reader opens the prompt that session's model gets (`GET api/threads/<id>/prompt`, `src/prompt-view.ts`). It reads the session's last captured payload, which the user-history extension writes on every model call (`src/prompt-capture.ts`); a session on another box has its capture read through that box's relay (`src/prompt-host-capture.ts`). Without a capture it rebuilds the conversation from the session file and says so in the header, in the facts and on a placeholder row for each part a rebuild cannot know. Each part is one payload block. The header switch picks one of two views, and the browser keeps the choice (`chat.promptMode`). Summary is the aggregate view: the parts before the conversation, then the conversation by source kind with token shares. In order (`src/client/PromptOrder.svelte`, `src/client/prompt-order.ts`) shows the payload in the order the provider reads it. An Anthropic request lists the tool definitions first, each named with who registers it, then the system blocks, each with its Prime source, with the skills list open per skill. After those, one row per incoming message: owner and agent messages, notices, wakes and compaction summaries. Each row opens into what followed it: the blocks the context hook added, thinking, text and each tool call with its result under it. A message that came in during a tool loop is marked mid-turn. In order draws its first 40 rows at once and adds the rest when the browser is idle. On frontend bro (458 incoming messages, 1.6 MB) on 10-22, its draw took 149 to 166 ms after the server's answer, against 77 to 101 ms for Summary.
- Images: a click on an attached thumbnail in the composer, on a pending image on the new-chat screen, or on an image in a user bubble opens it large over a dark backdrop. Esc, the close button or a click outside the image closes it; Left and Right, or the arrow buttons, move through the message's images. Focus returns to the image you clicked.
- Updates: the page carries its build id and the sessions stream reports the running build on every connect. After the service restarts on new code, an open tab reloads itself; when a composer holds an unsent draft or a chat is starting, a toast offers Reload instead.
- Saved threads open read-only in a few hundred milliseconds. Sending a reply resumes them natively.
- Account: the composer bar shows the thread's account by full email, with one meter per usage window in one style (label, percent, a 4 px bar that turns amber at 70% and red at 90%). Claude shows 5h and Week, plus the Fable weekly cap only when the current model name contains "fable"; Codex shows the windows its plan has. Hover shows the reset times. A click opens Settings.
- Throughput: the first row of the sidebar footer, above the Claude and Codex pool meters, is a live trace of output tokens per second for every agent on every box, read from LGTM (`src/client/ThroughputLine.svelte`): the rate every 10 s over the last 10 min from the `usage` feed as a thin area line, and the current figure over the last 60 s, "Output 1.5k tok/s". It follows the token kind picked in Settings > Usage (`usage.metric` in the browser), so Total shows "Tokens 236k tok/s" again. Hover shows the kind per second (with the total beside it), per minute and per day in full; a click opens Settings > Usage. When LGTM fails, the figure reads "err" in red and the hover shows the error, so a failure never looks like idle. The feed is subscribed only while the tab is visible, there is no animation loop, and a feed silent for 15 s dims the row.
- Agents: the second row of the sidebar footer counts the Prime Agent sessions running a turn right now (`src/client/AgentsLine.svelte`, `activeAgents` in `src/client/active-agents.ts`): each chat, thread or duty job whose own turn runs, plus its running subagents at any depth, the same rows the sessions stream already sends, so it matches the `rosterStatus` "running" count of `prime-agent sessions --all --json`. An archived thread's own turn is left out. The row reads "Agents  6 threads, 29 sub  35 active", and hover spells out both parts.
- Titles: every title is the native one, the same as the terminal agents view: the session name, else the first message the daemon reports (a skill invocation shows the typed text instead of the `<skill>` block). The chat stores no titles. Renaming sets the native session name, and the sidebar and the thread header both read the one row the daemon lists.
- Settings: a dialog opened from the account or the gear in the sidebar. Its tabs, listed in `src/client/settings-sections.ts` with an icon and a one-line description each: Accounts, Usage, New chats, Appearance, Phone access (see Phone access through Tailscale), Slack, Updates and How it works. New chats holds the model and effort every new chat starts with, the same `defaultModel` and `defaultThinkingLevel` in Prime Agent's settings.json the terminal uses, written through Prime Agent's own settings manager; it shows the same model menu as the composer (favorites, search, Effort row) and each pick saves at once. An open new-chat screen reads the new default at once, and a send with no model picked passes the shown default model and effort to the create request, so the label and the new session always agree. Accounts is the first section. It has a tab per provider, an "Add Claude account" or "Add Codex account" button, the sentence "This thread uses X (reason)", and one row per account: email, plan, one state badge (off, seat, pinned, depleted, cooldown, refused, needs login) and every usage window with its percent and "resets in 3h 46m". A click on a row only selects it and keeps its Use in this thread button in view. Only Use in this thread, on the row (shown on hover) or in its menu, moves the open thread to that account. Off rows are dimmed and show Turn on. Needs-login rows show Sign in again. The row menu holds Use in this thread, Refresh usage, Use a reset and Check resets (Claude), Pin or Unpin for all sessions, Drop seat, Check again (re-probe refused Claude accounts), Sign in again, Turn off or Turn on, and Remove, which asks you to type the email. Add account and Sign in again run `pi-pool login`: the page opens the sign-in page in a new tab, shows the Codex device code with a copy button or a paste box for the Claude code, and streams the status until it is done, failed or cancelled. One sign-in runs at a time and the service stops it after 10 minutes. Refresh all reads every account of the open tab now, and the refresh button on a row (on hover) or Refresh usage in its menu reads that one account. Both run `pi-pool refresh --stream`, which reads each account from its provider even if it was read a minute ago. While it runs, the button shows "Reading 3 of 8" and each row shows Queued, Reading, Updated or Not read; the table reloads after every read. When it ends, one line says how many accounts were read and names the ones that were not, and each of those rows shows the reason, for example a rate limit with the time of the next read. One refresh runs per provider at a time, and the last one stays visible to a page that watched it until dismissed. Claude accounts also show their banked usage-limit resets (`pi-pool resets`, read by Check resets on the Claude tab or in a row menu; nothing is read on open): a note per row such as "1 banked reset left: <grant label>. Expires Oct 23. Checked 4m ago.", a "1 reset" badge and a Use reset button when one can be spent now. Use reset asks first, with how many resets are left, which limits it clears, the current usage, and when the week resets by itself if that is within a day; it then runs `pi-pool reset` and refreshes that account's usage. A claim that got no answer shows a Reset unknown badge and Retry reset for 10 minutes, which resends the same claim.

- Usage: every agent on every box together, read from LGTM (see `src/usage/lgtm.ts` under How it works). LGTM counts input, output (reasoning included), cache read and cache write apart, and the page shows one kind at a time: a switch in the header (Output, Input, Cache read, Cache write, Total), Output by default because cache reads are about 95% of a busy hour and hide the generated tokens. The choice is saved in the browser (`usage.metric`) and the sidebar Throughput line follows it. Five headline cards update live from the `usage` feed every 5 s: the kind per second over the last 60 s, per minute over the last 60 min, over the last 24 h, each with the total under it (the output when Total is picked) and a sparkline (the rate every 10 s over the last 10 min, or per minute over the last hour); the prompt cache hit rate (cache read / (input + cache read + cache write), `cacheHitShare` in `src/shared/cache-health.ts`) over the last 60 min with the last 24 h under it and a sparkline per minute; and the cost since local midnight. Under them a bar chart of the kind over time: a window switch (1h, 24h, 7d, 30d), a bucket menu where the window offers more than one (1h is per minute; 24h per hour or minute; 7d per hour or day; 30d per day or hour), and a group switch: All, By host and By model stack the kind per key, up to 8 keys plus "other", with a legend; By kind stacks the four kinds in one bar, output in the accent colour at the bottom, input, cache write and cache read in fading tones of it, with a legend and a Tokens / Share switch beside it. Share draws every bar at full height with its parts as fractions, so a bucket's mix reads even where cache reads dwarf output; in Tokens a kind that was used at all is at least 1 px tall. Bars sit by time, so a quiet hour is a gap. Hover a bar for the bucket's time, the kind, the total, the cache hit rate, calls, cost and the per-key split (per kind with its share); the other bars dim. Below the chart, one row per host and model in the window: host, model, calls, the kind's tokens (every kind and the total on hover), the cache hit rate, cost and the output tokens per second of generation time, sorted by the kind. When a query fails, the page shows the LGTM error in place of the numbers. The chart and table load on open and on each control change, and again on a feed update at most every 20 s. Window, group, kind and the Share choice are saved in the browser. The chart is hand-drawn SVG; no chart library. LGTM holds no usage from before the Prime build that exports it (10-19).

- Updates: the Prime Agent daemon version (from `daemon_hello.appVersion` on each connect), the prime-agent package the chat loaded, and the chat build. When the daemon reconnects on a new version, the chat runs `scripts/sync-prime-agent.mjs` once for that version. The script reads which prime-agent SDK that release ships from its `prime-agent` tarball: from 0.10.0 the daemon is a Rust binary and its package names the TypeScript SDK it still ships in `primeAgentTypeScriptFallback.version` (0.10.0 ships 0.9.8), else the SDK is the release's own version. `sdk.json` keeps that answer, and Settings shows the SDK the daemon ships. When the chat already uses it, the panel says matched and nothing restarts. Otherwise the script points the root and chat `package.json` at that SDK release, installs, runs the chat type check and tests, and restores the old package files if any step fails. On success the login item exits 75 and launchd starts it again on the new packages; open tabs reload. A failure shows its message with Retry and is not retried on its own for that version. The switch "Update the chat when Prime Agent updates" turns this off (saved in `sdk.json`). Below it, Chat rules lists the brief version each chat loaded, and Update all chats reloads every chat onto the current brief: an idle chat at once, a busy one when its turn ends.

Keyboard: Cmd+N new chat with the composer focused, Cmd+K opens the Agents view with its search focused and closes it when it is open, Cmd+B sidebar, Esc closes menus or stops a busy thread when the composer has focus, arrows and Enter move and pick in lists and menus. Use `/compact` in the composer to compact context.

Look: the Virev tokens (graphite neutrals, ocean accent, raised menus with a strong hairline and a float shadow, flat mode switches) ported into `src/client/app.css`. Every toast has a close button, including the ones that stay until acted on, such as Reload. Tooltips appear only on icon buttons. All spinners turn in one phase, one page clock drives every timer, and it stops while the tab is hidden. Light and dark follow the OS unless Settings > Appearance picks one. Appearance also picks the accent color (Ocean, Violet, Green, Amber, Rose, Graphite). The choice is saved in the browser under `chat.appearance`, applied at once, and set as `data-theme` and `data-accent` on `<html>` (`src/client/appearance.ts`), which `app.css` reads; the defaults set no attribute, so the look stays as before. The theme also sets both `theme-color` metas, so the installed app's title bar follows a forced Light or Dark and not only the OS scheme. In macOS full screen Chrome keeps that 38 px title bar until View > Always Show Toolbar in Full Screen (Cmd+Shift+F) is off in the app window; no page setting can hide it. Below 900 px the sidebar becomes an overlay.

## How it works

```text
browser  <- WS api/ws, feed sessions --- Catalog: one DaemonClient, roster_subscribe, list all
browser  <- WS api/ws, feed thread ----- ThreadHub: one DaemonAgentConnection per open thread
browser  -> POST api/threads/:id/prompt  ThreadHub.prompt -> connection.prompt(...)
```

- `src/chat-catalog.ts` keeps the session list. It subscribes to `roster_update`, refreshes `list all` and `cron_list` after a short debounce, merges tags and priority from `src/chat-labels.ts`, and pushes the projected rows and tags to every open browser.
- `src/chat-threads.ts` keeps an attached connection per thread (up to 8 live, idle ones close after 3 minutes). On subscribe it sends one snapshot, then forwards native events. `message_update` is coalesced to one per 40 ms.
- `src/chat-projection.ts` trims payloads without renaming anything: tool output over 600 characters and tool arguments over 400 get `truncated: true` and a fetch endpoint (the text of a `tell_owner` call keeps up to 24000, because the chat feed shows it as the owner's bubble), thinking is cut to 240 characters, image bytes become `api/images/<hash>` URLs from a bounded memory store.
- `src/shared/thread-state.ts` is the reducer. The server and the browser apply the same events to the same `ThreadState`, so there is no polling and no DOM diffing.
- `src/shared/turns.ts` groups messages into turns for display. A user message always starts a turn; an agent message or background completion starts one only after the previous run settled.
- `src/shared/cache-health.ts` reads native per-call `usage` and flags broken caching.
- `src/usage/lgtm.ts` is the only source of token usage in the chat: Settings > Usage, the sidebar Throughput line and the Agents card tok/s. Each Prime process on every box exports its model calls as OTLP counters (`prime_agent_tokens_total` by `kind`, `prime_agent_cost_USD_total`, `prime_agent_calls_total` and the per-session `prime_agent_session_output_tokens_total` and `prime_agent_session_generation_seconds_total`, labelled `box`, `model` and `session`), and Alloy writes them to the staging estate Prometheus. `Usage` runs PromQL through Grafana's datasource proxy (`estate_prometheus_stg`) with the Viewer token in `<data dir>/grafana-alerts.json`, the same file the alert bridge reads, and every query filters `job="prime-agent"`, because test runs export the same series under another job. The exporter's kinds `cache_read` and `cache_write` become `cacheRead` and `cacheWrite` at this boundary. Nothing is queried until a page subscribes to the `usage` feed, opens the chart or the Agents card asks for rates. A failed query reaches the feed as `{ state: "error", error }` and the chart routes as a 502, never as zeros. The read contract is `~/work/otel-tok-meter/CONTRACT.md` on both hosts.
- `src/client/` is the Svelte 5 app. `src/client/ui/` holds the shared controls: `Floating` (top-layer anchored panel), `Select`, `DateRange`, `Checkbox`, `TagPicker` and the `tooltip` action. `src/client/usage.ts` holds the pure helpers behind Settings > Usage (number formats, the bucket per window, the chart layout). `chat-assets.ts` bundles it in memory with esbuild in a worker thread (`chat-assets-worker.mjs`) once the service listens, and serves it with an ETag; the page and app.js wait for the build, the API answers at once. `chat start`, `stop`, `url` and `status` load prime-agent only when they need its default paths (about 1 CPU second).
- Diagrams: `src/chat-render.ts` serves `render`, a page embedded only as `<iframe sandbox="allow-scripts">`, and `render.js`, built on first use from `src/render/main.ts` with mermaid (about 5 MB). Chrome keeps no HTTP cache for an opaque-origin frame, so the chat page fetches `render.js` once and posts it to each frame as a Blob, which the frame's one inline boot script loads. The sandbox gives the frame an opaque origin, so it cannot read the chat's storage or call its API, and the chat page keeps its strict CSP (it only adds `frame-src 'self'` and `https:` images). The frame has its own policy: inline styles for mermaid's SVG, scripts only from its boot script and `blob:`, no network. `src/client/diagrams.ts` posts `{ type: "render", id, kind: "mermaid", source, theme }` to the frame and sizes it from `{ type: "size", height }`; wide drawings shrink to 70% and then scroll sideways. The second kind is `page`: `{ type: "render", id, kind: "page", html, theme }` carries a wiki page's HTML, which the frame parses with `DOMParser`, copies through a tag and attribute allowlist (scripts, styles, forms, embeds and inline SVG dropped with their content; `javascript:` links and non-https image sources removed), draws each `<pre class="mermaid">` with mermaid, and reports `{ type: "open", href }` for a clicked link and `{ type: "image", index, src }` for an image named by path, which the chat answers with `{ type: "image", index, blob }` from `api/local-image` (the frame's policy allows `blob:` and `https:` images). The `pageFrame` Svelte action owns one such frame. Another block kind (charts) is a new `kind` in the frame.
- `src/chat-pool.ts` wraps `components/pi-pool/bin/pi-pool` with argument arrays. `poolCommand` holds the exact command lines for off, on, rm and login. `AccountLogins` runs one `pi-pool login` child at a time: stdout JSON lines become the login state, a pasted code goes to its stdin, cancel closes stdin, then SIGTERM and SIGKILL follow; its own deadline backs up `--timeout 600`. It never runs `pi-pool-token`. It drops the calling session's variables, so pi-pool resolves only the thread named with `--session`.

## Chats

A chat is a thread kind: a Prime Agent session that is the owner's chat partner for one topic ("let's develop feature X"), created from the New chat screen with the Thread / Chat switch. It keeps the normal per-thread workspace (the repository it is responsible for), model, account, effort, name, labels and archive. It talks like a DM, does only quick read-only look-ups itself, keeps a board the owner sees (plan, owner todos, scratchpad bullets with links), and starts jobs with `rlm.spawn` (children in its repository) or `rlm.create_session(..., cwd=...)` (another repository), relays their reports, and forwards the owner's answers.

- Index: `<data dir>/chats.json` (`{ ids }`, newest first, an `IdIndex` from `src/id-index.ts`) is the chat side's one definition of "chat". `src/chats.ts` owns it. Rows in the sessions feed carry `chat: true` from it, so the sidebar sections chats apart. Archive from the sidebar works as for any thread and drops the id from the index. Undo (`POST api/threads/:id/unarchive`) keeps a chat a chat: the session file still carries the `chat_mode` entry, so `Chats.restore` puts the id back in the index, pins the chat and sets steering `all` again. A plain thread stays plain. The board file is not touched by archive, so it comes back as it was.
- Mark: the server creates the session with `config.extensionFlagValues: { chat: true }`. `extension/index.ts`, at `session_start` of a depth-0 session with that flag and no mark yet, writes the session entry `chat_mode` (`pi.appendEntry`), and on every later start finds it with `ctx.sessionManager.getEntries()`. The entry is the agent side's one definition. Children (depth 1 and deeper) inherit the flag through the runtime config but never get the entry.
- Brief: the extension registers the tool `chat_board`, whose `promptGuidelines` carry the chat brief (`CHAT_BRIEF` in `src/chats.ts`). The brief holds one short line per rule, about 6,500 characters. A rule the brief holds names its correction id, like `(c47)`, and `BRIEF_CORRECTIONS` collects those ids. Rules for one kind of action live in the board skill and are read on demand: `skills/board/SKILL.md` for plan shape, upkeep, gates and targets, and `skills/board/references/` for jobs, check-ins, git, owner asks and corrections. The brief's last lines point there. In a marked root it adds the chat tools (`chat_board`, `tell_owner`) to the active tools (`pi.setActiveTools`), which rebuilds the base system prompt, so the brief reaches agent-message wakes and heartbeat turns, which skip `before_agent_start`. Children drop the inherited tools. A job of a chat gets one line of its own: at `session_start` a depth-1 session whose parent session file carries `chat_mode` (`fileChatName` reads the parent's name from the head of that file), or a depth-0 root that `<data dir>/chat-jobs.json` lists by its session id (a duty job) or its session name, registers the tool `job_reply`, whose one guideline (`jobReplyGuideline`) says it is a job of that chat and, when it finishes, fails or gets blocked, must send its report first, with `receiver_role="parent"` (a subagent) or `receiver_role="sibling", receiver_name=<chat>` (a root), leading with the answer, and that it works, reasons and writes in English, quoting the owner's words as-is, with docs and wiki pages in English too and only chat replies to the owner in his language (c2, c102), and that every tree, rig and data copy the job or its subagents make to throw away goes under the job's own folder `~/scratch/<its session id>/` (`jobScratch`), never in a wiki session folder or under `~/.prime/agent/session-artifacts`, and exports only the paths the job builds or tests. A job's end deletes the scratch folders of its sessions and the paths their `owned.json` records name (`endOwned` in `src/job-leftovers.ts`), and keeps one that a process runs in, holds or names until a later sweep finds it free. It never deletes a path a transcript only names. The chat, each job and every subagent under either register the tool `poteto_mode`, whose one guideline (`personaGuideline`) points at the poteto-mode skill, so every turn of them works in poteto-mode (owner, 10-15). In every session the extension's context hook shortens Prime's `[python-state]` and `[python-state-restored]` notices to a name count and each refinement notice to `Refinement saved: <title> (<id>)` (`src/prime-notices.ts`), a pure function of each message, so the cached prompt prefix stays the same. When the owner stops or archives a job through the chat's controls, the service records his cancel in `<data dir>/job-cancels.json` before the abort or kill, with `by: "owner"`. A chat that owns the job can ask for the same Stop or Archive through the same routes with `{"by": "chat", "chat": "<its session id>"}` in the body, and the record then says `by: "chat"` with that chat, since on 10-21 a job stopped vent's finished job at vent's request and the record could only say the owner asked. Both hold the same way. The parent's hook rewrites Prime's `[child-exited: no-reply ...]` for that child to `[child-exited: cancelled ...]` with "stopped by the owner at HH:MM" (or "by chat <id>") and "don't reopen it", and the failed-turn wakes, the job-end, no-report and open-steps notices, the check-in's pushes and steers, the waiting-job restart and resume_paused.py skip the job until the owner sends to it or unarchives it (`src/job-cancels.ts`, `Chats.cancelJob`). Prime writes owner_stop or owner_archive on every archive the service sends, so each archive the service makes on its own, such as the duty runner's archive of a finished duty job (`duty_job_end`), a chat's sweep of an idle root (`idle_root_end`) or a spare, failed create or script teardown (`service_cleanup`, the archive route's `by`), is one operation in `<data dir>/service-archives.json`, written before it goes out with the id of the session file's last entry, and records no cancel. Once Prime confirms it, the operation names the id of the one archived line it wrote, and `ownerStopSinceActive` and resume_paused.py read only that exact line as the service's (`src/service-archives.ts`). A refused or failed send names no line, and a later owner stop or archive is a line of its own, so both stay the owner's. The chat's extension writes `chat-jobs.json` on `tool_call`, from the plain string `name=` of each `rlm.create_session(...)` in the cell (`createSessionNames`; entries older than 30 days go on the next write). A root named after its `session_start` looks again at its first `before_agent_start` and adds the line to that turn's system prompt. When a chat's direct subagent first shows up, the server reads its brief (the `prompt` in `session-artifacts/<chat>/<child id>/rlm-subagent.json`) and checks it from its `Split:` line on for a gate nobody asked for or a wait for another thread's go or the owner's ok (`briefCheck` in `src/shared/brief-check.ts`, c47). A gate passes when a negation or a rejected option sits earlier in its own clause ("No source redesign or extra review round is needed"), when it names a wait as a quantity to measure ("queue wait for a slot"), when it waits on a production step (c74, c154), or when its sentence gives the cause or the owner rule behind it. On findings the chat gets one `[brief check]` steer naming the job, each finding with its fix. The spawn is never held. Each job is checked once across restarts (`<data dir>/brief-checks.json`), and a job spawned more than 30 minutes before the server first sees it is skipped. Roots a chat starts with `rlm.create_session` are not checked.
- Feed: the chat reads like a DM between the owner and the VP. Who started a turn decides what shows (`chatLines` in `src/shared/chat-feed.ts`, tracked the way `buildTurns` does: a user message, `[board] ` lines included, starts an owner turn; an agent message, a check-in, a job notice or a background completion starts an agent turn when the last run had settled, and joins the running turn otherwise). On an owner turn the chat's text shows as bubbles, as does a streaming reply. A reply shows whole at any length, with its diagrams and images. On an agent turn its text never shows; the only way the chat reaches the owner there is the tool `tell_owner` (`{ text }`, refused only when empty, result "told the owner"), whose text shows as a normal agent bubble on any turn; each call is its own bubble, so a chat may send 2 or more in one turn. No code checks a reply's words or length; the reply rules live in the chat brief (c97). Everything else is a background line: inbound agent messages, the chat's hidden text, the waits for a Claude account, "Reply stopped", "Prime Agent restarted", compactions, check-in changes and the server's notices. A run of them between two visible lines folds into one muted row with its most recent line and a count, "Waiting for a Claude account until 09:22. · 23 updates from check-in, chat-057a, babysitter and 4 more" (`foldLines`, `foldLabel`; up to three senders, newest first). Of the waits in a run only the latest stays. The row opens the reader with the list, each entry with its sender, time and whole text, the chat's own hidden text labeled "VP notes" and a notice labeled "Notice". An error that ends an owner turn stays visible on its own until an answer follows it, as does the live wait under his unanswered message. Time stamps go only above visible lines, when 15 minutes passed since the visible line before (`stampedItems`), so none sits between folded rows. Job notices and background completions themselves produce no line. The server's own steers, `[check-in] ` and `[job] ` user messages (`serverNote`), show as fold entries from "check-in" and "jobs" and start an agent turn, not an owner turn. Sender names are display names: `child:<name>` is the job's name, a session name stays, and a session id or a live agent's 12-hex id (`SessionRow.agent`) resolves through the catalog rows (`catalogNames`) and reads "another thread" when nothing lists it. The typing dots show only on an owner turn.
- Feed scroll: the feed opens at the newest line and draws a window of its items (`feed-window.ts`): the newest 30, then 30 earlier ones each time the owner scrolls within a screen of the top, loading the older page when every drawable item shows. While older pages are unloaded the window starts at the first owner message, because the lines above it belong to a turn that started on the older page and can still turn into quiet lines and fold when it loads. So it reads on through pages until one holds a message the owner typed and merges them as one page (`olderPages`), which draws the feed once: on 10-22 the AI harness chat read 15 to 17 such pages at the first scroll up, and on a busy box drawing each one in turn took 1.6 to 3.3 s (median 2.9 s) against 0.8 to 2.1 s (median 0.9 s) as one merge. A window holds at most 90 items, so drawing on one end takes items off the other, out of view, and later ones draw again as he scrolls back down. The window's ends are items, and an end that an older page folds into an earlier run moves to that run, so the view never jumps back to the newest items. `holdPlace` keeps the view in place before each frame paints: at the bottom while the owner is there and the window reaches the newest, else on the row in the middle of the view, through rows drawn above or below, an older page, and a picture, diagram or embed that loads late; a row there that grows a quote when its older page loads grows upward. Jump to latest and a send go back to the newest items, and a message link loads older pages until it can draw the message.
- Build: a chat session loads the extension once and keeps running it, so after a service restart with new code it would still run the old tools and brief. `extensionBuild()` hashes `extension/index.ts`, `src/chats.ts`, `src/shared/chat-board.ts` and `src/shared/chat-feed.ts`; `<data dir>/extension-loads.json` records the build each chat last loaded (set at create, dropped at archive). Whenever a chat attaches (service start through `Chats.adopt` and the pin, a resume, an undo), a chat whose record differs is sent the daemon `reload` command, at once if it is idle, else at its next `agent_end` (`reloadAction`); the record then matches, so a plain restart reloads nothing. The board gates do not wait for that reload: a `chat_board` write goes to the live service (`POST api/threads/<id>/agent-board`, `src/agent-board.ts`), which judges it with the release's gates and the `releaseGo` switch, and the session applies it with its own copy only when no service takes it.
- Board: each chat has one board file, `<data dir>/boards/<sessionId>.json` (`ChatBoard` v2 in `src/shared/types.ts`): the plan (a nested checklist of goals and steps, statuses `todo`, `doing`, `done`, `blocked`, `dropped`, each step linked to its job by name), the owner's todo list (asks to the owner: a decision, a login, an approval; each may offer 2 to 4 `choices` of up to 80 characters, the agent's recommendation first; the owner taps a choice, checks, edits or answers it). The board has no scratchpad: the owner removed it on 2026-10-15, and a chat puts each decision in the note of the step it concerns. The plan nests to any depth and holds up to 500 items; a `plan_add` under a done goal sets that goal and every done goal above it back to `todo`, and the summary says so. A step may carry `waitUntil` (an ISO date-time, stored as UTC `toISOString`) and `waitFor` (a short text naming the event, up to 200 characters); `plan_set`, `plan_add` and `plan_update` set them, null clears them, and the check-in leaves such a step alone while it waits (see Check-in). Two writers, one path: the agent's `chat_board` tool (`{ ops }`; a call with ops returns only the op summaries and one line `Board rev N: X open steps, Y open todos.`; a call with no ops returns the open checklist (`renderOpenPlan`): `This chat: thread:<sessionId>` so the agent can link to its own thread, the check-in line, the goals and steps that are open or hold an open step, one line each, the open todos, and one line counting what it left out. The `board` Python skill (`skills/board` in sieun-pi, pre-imported in every kernel) reads the rest from the board file: `board.open()`, `board.get(id)`, `board.find(text)`, `board.done(since)`, `board.todos(all)`; its SKILL.md holds the op rules the tool description points to) and the owner's `POST api/threads/:id/board`. Both apply ops through the pure reducer `applyBoardOp` (`src/shared/chat-board.ts`) under the locked-json lock (`src/chat-board-store.ts`), all ops of a call or none; `rev` rises by one per op, ids are `p1`, `t1`, .... Ops: `plan_set`, `plan_add`, `plan_update`, `plan_remove`, `todo_add`, `todo_update`, `todo_remove`; a `scratch_add`, `scratch_update` or `scratch_remove` op is refused with `SCRATCHPAD_REMOVED`, which tells the chat to use the step's note. The owner may use the todo ops; the plan is the agent's. The agent may leave any number of its own todos open, since a clarifying question is welcome (c96). A todo with no choices that only holds a place for something not ready (`placeholderTodo`: the text starts with "Read:", or says "lands here", "link lands", "when ready", "when it's ready" or "when it is ready"; owner 10-09, correction c14) belongs in the plan, with its link sent in a chat message when it exists. Chat health counts the open ones as `placeholder_todos`. `parseBoard` refuses a file that is not v2. The extension finds the directory from the `agent-chat-data-dir` flag, else `<agentDir>/browser-chat`, the same as the server. The server reads the board into a chat's thread snapshot (`board`, null before the first op) and watches the boards directory: a change from either writer reaches the open thread's listeners as a `{ type: "board" }` event. After an owner change the server sends the chat a steer whose text starts with `[board] ` and says what the owner did (`[board] Owner chose "Wait for QA" for "Deploy now?"`, `[board] Owner checked "Log in to Stripe"`); the client shows such a message as a small owner-action line.
- Artifact links: a link is `{ label, target }`, and `target` is one of `job:<name>` (that job's latest report in this chat), `thread:<sessionId>` or `thread:<sessionId>@<timestamp ms>` (a thread, or one message in it), `wiki:<path>` (an llm-wiki page, read through `GET api/wiki-page`), `file:<absolute path>` (a text file, read through `GET api/local-file`), or an `http(s)` URL. `normalizeArtifactTarget` (`src/shared/artifact-link.ts`) stores pasted text in that form: a chat URL ending in `#<sessionId>@<ms>` or `#<sessionId>` becomes `thread:`, a wiki page URL becomes `wiki:`, a bare absolute path becomes `file:`; the reducer refuses anything else.
- Permalinks: the page hash `#<sessionId>@<timestamp>` opens that thread, chat or plain, and scrolls to the message whose `timestamp` it is, highlighted for 2 s; with no exact match it lands on the nearest message in time, so a link copied in a job drawer (the chat's receipt time) finds the job's own reply. A link to one reply is that hash, or `thread:<sessionId>@<timestamp>` on the board. Copy link sits on hover (long press on a phone) beside every bubble and job line of a chat, every prompt and reply of a thread, and every message in a job drawer, where it points into the job's own thread.
- Board panel: the cards Plan, For you, Duties and Agents, each folding from its header; Plan keeps the fold in the browser (`chat.boardCards`), For you opens whenever an ask is open. Plan steps are a tree: every item with children starts folded (`chat.boardItemsOpen` keeps what the owner unfolded, per chat), each shows an id chip (its board id in mono with a dot colored by a hash of the chat and item ids; a click copies the id), and a parent shows "n of m done". Done and dropped steps are hidden; a "Show done (n)" toggle per parent (and one for the top level, `chat.boardShowDone`, per chat) reveals them; the Plan header counts "n of m done" over the whole plan, and a goal reads as done only when the chat marked it done. An ask shows its choices as buttons, the first marked recommended; one tap, or Enter in the reply field that "Reply…" opens, saves the reply and checks the ask, and answered asks sit behind "Done (N)". A todo's link chips (job, message, wiki, file, web) open the reader, the thread, or a new tab. On a wide window the panel's left edge (a grip, brighter on hover) drags it between 280 px and 60% of the window (double-click puts it back to 320, Left and Right nudge it, `chat.boardWidth` keeps it); below 900 px it is the Board tab. Each row reads as one paragraph: fold, status mark and id chip sit inline before the text and a wrapped line comes back to the row's left edge; blocked is a muted ring with a slash, done a muted check. A step with an owner (`job`) has no pill: its text is the link, opening the job drawer for a subagent of the chat and the thread for a session. The chat's jobs live in the sidebar under its row (the chevron on a chat row): status, name, activity and age, running first, including the sessions it started with `rlm.create_session` once the chat is open; a job row opens its drawer in the chat. The Agents card lists the same agents, and a row's count ("3 sub", `agentSubagents` in `src/client/board.ts`) is every subagent that agent spawned at any depth, finished and deleted ones included: the daemon drops a subagent from its list once `rlm.delete_subagent` removes it, so the catalog also counts the `sub-*` folders holding an `rlm-subagent.json` under the agent's session folder (`spawnedSubagents`, read again at most every 30 s) and keeps the larger of the two. A dot before the count marks that some still run, the title reads "3 subagents, 1 running", and an agent that spawned none shows no count.
- Plan view: an "Open plan" button on the Plan card header (`PlanView.svelte`, `store.planView`) opens the whole board in one modal (min(1100px, 94vw) by 88vh, full screen on a phone, Esc closes): the plan as a tree with every level open, each step with its status mark, id chip, owner chip (opens the job drawer or the owner's thread) and note. Done and dropped steps hide until "Show done (n)" is on; "Collapse all" / "Expand all" folds every parent. A double click on a board panel row, its hover "open" button, or a mention chip opens the view on that item: its parents unfold, done items show when it is one, and the row scrolls into view and lights up for 2 s (`focusPlan` in `src/client/board.ts`). The view follows the board live.
- Reader: every artifact opens in one modal (`Reader.svelte`, `store.reader`, min(960px, 92vw) by 86vh, full screen on a phone), from a note chip, a job line in the feed, a message in the job drawer, or a link inside a rendered reply. `store.openArtifact(target, thread)` decides through `readerAction` (`src/client/reader.ts`): an `http(s)` URL opens a new tab, a bare `thread:<id>` opens the thread, everything else the reader. `job:<name>` shows the job's latest message to the chat in full with its earlier messages behind a fold and "Open full thread"; when that message names a wiki page (`reportWikiPage`: a `http://localhost:5176/page/<path>` URL, a `wiki:<path>` target, or an `apps/llm-wiki/content/<path>` path ending in `.html` or `.md`), the page is drawn under the report in a "Full report: <title>" section with "Open report" (a new tab on the wiki); the preview card names the same page on a "Full report: <title>" line; `file:<path>` shows markdown rendered, a `.diff` or `.patch` with line colors, anything else as code with line numbers; `wiki:<path>` shows the page itself with "Open in wiki": a `.html` page's own HTML in a sandboxed `render` frame (the frame's allowlist keeps document markup, draws `<pre class="mermaid">` blocks with mermaid, asks the chat for the page's file images by postMessage and hands link clicks back, so a link to another wiki page opens in the reader and any other link in a tab), a `.md` page rendered as a reply is; `thread:<id>@<ms>` shows that one message with "Go to message". The header carries the source and "Copy link", which copies a form the Add a note field turns back into the same link (the page URL with the message hash, the file path, the wiki URL). The job drawer keeps the job's status, brief and a one-line preview per message; each preview and "Read report" open the reader.
- Replies: an agent bubble renders markdown the way a thread reply does (lists, inline code, code blocks with Copy, bold, tables in a scroll box, links, images, mermaid), with tight bubble spacing and headings as bold lines. A board id written as a whole word (`p7`, `s3`) that is on the chat's board becomes a mention chip (the item's dot color and id, its first 60 characters on hover) in agent and owner bubbles and in the reader's update lists, inside lists, tables and bold too; an id inside a code span, a code block or a link, or one the board does not have, stays text (`mentions` extension in `src/client/markdown.ts`, keyed on the board rev in the render cache). A chip opens the plan view on that item. A web link opens a new tab; a link whose target is an artifact (`job:`, `thread:`, `wiki:`, `file:`, a bare absolute path, or a chat permalink URL) opens the reader or the thread. An image or a mermaid fence that stands as a block of its own (`bubbleBlocks` in `src/client/markdown.ts`) becomes a wide card under the bubble, up to the feed width, several stacking; one inside a sentence or list stays inline. A diagram card draws once its fence closes, also while the reply streams. The owner's own bubble renders links, inline code, bold and line breaks only.
- Guard: in a marked root the extension blocks every shell command except quick look-ups: a command (the `bash` tool, a `bash(` literal, a `!` line) passes only when it starts with `prime-agent`, `git log`, `git status`, `git diff`, `git show`, `rg`, `ls`, `cat`, `head`, `tail` or `wc` as a whole word and has no `;`, `&`, `|`, `<`, `>`, backtick, `$(` or newline outside quotes. A computed `bash(` command and `%%bash`, `%%sh`, `%%zsh` and `%%shell` cells are blocked. Calls are found with string literals and comments blanked, so a job brief that mentions `bash(` passes. `rlm.spawn` and `rlm.create_session` are allowed. Any error fails open.
- Sends: every message to a chat is a steer (`POST api/threads/:id/prompt` ignores `mode`), and the server sets steering mode `all` on every attach, so consecutive job reports batch into one turn. The owner's send to a chat he archived reopens it before the message goes (`Chats.reopen`): the session resumes, then the chat leaves `archived-chats.json` and goes back into `chats.json`, so its turn runs as a chat and GET agents answers. A resume that fails keeps it out of the chat list, though its session file already reads active. An archive that lands before the message goes stops that send with a 409 and leaves the chat archived, and a failed sidebar update after the reopen is logged and holds nothing back. An agent message or a wake that resumes an archived chat leaves it archived. Stop sends `resume_queue` right after the native abort, because an abort suspends the session's input pump and an agent message to an idle suspended session is refused until then. In a chat and in a job of a chat, `agent_message.send` returns `deliveryStatus: "unconfirmed"` with a note in place of the daemon's `Timed out after 30000ms waiting for the Prime Agent daemon response to "send_message"` error (`src/message-limit-check.py`, p334). The supervisor waits 30 s for the target's worker, and a busy worker answers later but still queues the message: on 10-12 both sends that timed out at 17:08Z landed, in frontend bro at 17:10:13Z and in Crawler VP at 17:16:20Z, when each one's ipython call ended. Senders that read the error as a failure sent again, and frontend bro got one ask 7 times. The wrapper names itself `rlm.host_request`, and its install points every module that holds rlm's own function at it, because a kernel revive pickles each skill module by value and dill pickles a function by value when its name finds another one. On 10-16 such a copy of rlm's `host_request` lost rlm's package, and `agent_observe` raised "attempted relative import with no known parent package" (`test/kernel-revive-host-request.test.ts`).
- Residency: chats are pinned (`ThreadHub.pin`, up to the live limit of 8): never swept or evicted, resumed again on each catalog update that finds them not live. These resumes are background attaches (`AttachQueue`): at most 2 attach at a time (`BACKGROUND_ATTACHES`), in pin order, while a tab opening a thread or an owner send attaches at once and promotes a chat still waiting; stall checks (`view`) and the Slack bridge also attach in the background. A failed resume (a daemon timeout) is tried again after 15 s, doubling per failure up to 5 min. A session the daemon lists as active but does not hold (`Unknown active session`) opens saved; a job wake that finds its thread gone (that answer, or not in the catalog) logs one line and skips it until it shows new activity. At service start every chat in the index is pinned again; one the daemon does not list is forgotten, with a log line. One the daemon lists as archived is unarchived and pinned: the archive route forgets a chat when it archives it, so an archived chat still in the index was archived by the daemon (`prime-agent shutdown --force` and an update restart write the archived state into every live session; on 2026-10-12 a forced shutdown made the serve drop all 9 chats). The archive route also writes the chat into `<data dir>/archived-chats.json` (`Chats.archive`), and the owner's unarchive or his next send takes it out (`Chats.restore`, `Chats.reopen`). An agent message to an archived session resumes it (2026-10-12: a relayed broadcast resumed "stripe and payments" 4 hours after the owner archived it, and the scan took it back as a chat). Such a session may wake and answer, and nothing archives it again (owner 10-12: "the thread should be able to respond, but not be in the Chats list"), but the scan never re-adopts one, so it gets no brief reload, check-in or duty, and its sidebar row stays archived (`Chats.archivedIds` in the catalog projection). A chat in that file found in the index at start is forgotten, not unarchived. At start and every 10 minutes (`ADOPT_SCAN_MS`) `Chats.rescan` reads the head of each unarchived thread active in the last 7 days that is not in the index; one whose session file has the `chat_mode` entry (it precedes the first message, so the read stops there) is restored as a chat and logged (`re-adopted`). A thread with messages found plain is not read again. This brings back a chat unarchived outside this server, as chat-6394 was (archived 2026-10-07 15:18 UTC, unarchived 15:23, then 0 check-ins). The scan skips one whose session file records the owner's stop or archive (`owner_stop`, `owner_archive`) after its last active state and files it in `archived-chats.json`, and the archive route archives a session with the `chat_mode` entry as a chat even when the index never held it: on 2026-10-20 a clean-room setup archived stray chat 01a157fb, which its create had made just before a service restart, and the scan resumed it 3 s later. An archive whose only open part is a recorded retry of its scheduled-job cancel answers 200 with that notice, and 502 stays for a cancel no retry holds.
- Check-in: the server, not the model, runs each chat's check-in every 15 minutes by default (`CHECK_IN_MS`, each chat can change it, `src/chat-checkin.ts`), and every run has two parts (owner 10-09: "every (n min/h/day) -> code precheck -> run job with that context"; "control flow should be dynamically defined by agent"). First a code precheck with no model call (`checkInPrecheck`): it lists the jobs, the chat's direct subagents (the thread's `rlm_child_update` events and snapshots, with `repliedSinceTask` and `lastActivityAt`) and every thread an open plan step names as its owner (the catalog rows, with status, last activity and message count). A step's owner is its `job` (a child name or id, a session name or id, or `thread:<id>`; the board reducer stores `thread:<id>`, `thread:<id>@<ms>`, a pasted chat URL and `job:<name>` in the bare form), else the first `thread:<id>` link in its note. The chat's own steps (its session id or name as owner) are no job. Every open leaf step (an open item with no open child; a goal once no step below it is open) gets one class (`stepClass`): `live` (its owner is a job at work, a thread active in the last 2 hours, or the chat itself on a step it changed in that time), `foryou` (an open agent todo names the step or one of its PRs, or shares a distinctive word with it, `todoForStep`), `waiting` (`waitUntil` still ahead, or `waitFor` or a thread owner with progress in the last 2 hours), `due` (`waitUntil` passed and the step has not changed since), `stale-chase` (it waits on another thread or an event with no progress for 2 hours, `STEP_STALE_MS`) or `orphan` (no live owner, no todo, no wait). The precheck also finds the open items that look done (`looksDone`: every step under it closed, or a note that says shipped, merged, deployed, landed, released or live), the open steps on another thread's work by a ledger handoff (`scopeMisses`), the goals nobody works on (`idleGoals`: no live step and an orphan step that does not look done; correction c11), a board the server cannot read, more than 3 open agent todos, steps that can start, and blocked steps that wait on the owner with no question in For you. A chat with no job at work, no open plan step, no board read error and no ask overflow has nothing to check and starts nothing. Then the duty runner starts one check-in job with that as context (`Duties.checkIn` in `src/chat-duty-run.ts`, `src/chat-duty-job.ts`), whatever the measure says: a met target is information, not a pass. The job is a root session the server creates in the chat's folder, named like `check-in 14:00` (`dutyJobName`), registered in `<data dir>/chat-jobs.json` under the chat's name by its session id before its first message, so it gets the job reply guideline, shows in the chat's Agents card as a root, and reports to the chat with `receiver_role="sibling"`. Its brief (`dutyJobBrief`) holds the duty's goal and the owner's words, the measure against the targets, the findings (`checkInPrecheckText`: goals nobody works on, the class line of each due, stale-chase and orphan step with the thread to chase, the items that look done, the scope lines, job ends the board does not show, the other facts, the jobs, and every open step oldest change first, at most 30), and how a chat job works: check the real state, fix what it finds, decide its own control flow, split work by the job rules, message other threads itself, send the chat board ops, end in one short turn and send nothing when nothing needs work. The check-in's own focus (`CHECK_IN_FOCUS`) adds keeping every agent's work in line with the plan and For you, fixing jobs that gave up, stalled or died, and starting parallel jobs for open goals with independent work and no live job. One job per duty per slot: a run whose slot already has a job starts none (so a re-entrant tick or a restart cannot double it), a run while the duty's last job still works starts none and is recorded as `skipped: previous run still working (job <name>)`, and a run that starts a job archives the last one and drops it from the registry, so the Agents card lists only the current one. The server sends the chat no check-in line, no nudge to other threads and no board note. The check-in is each chat's one built-in duty (`CHECK_IN_DUTY`, id `checkin`, correction c15; its goal is the owner's 10-09 definition: it steers the agent swarm, keeps every agent's work in line with the plan and For you, is the owner's interface, and fixes agent quirks). Each run is recorded in `<data dir>/duties/<chat>.runs.jsonl` with its slot, its job, its step counts per class, its flagged steps and seven targets of 0 measured from the same classes (`convergenceMisses`: `orphan_steps`; `due_late`, a step due for longer than the chat's check-in interval; `stale_chase_24h`; `job_end_unrecorded`, a step whose job ended longer than one interval ago and after the step last changed; `job_end_silent`, the same for a job end the server told as a bad end with no report, counted there and not again in `job_end_unrecorded`; `scope_misses`, an open step on another thread's work; `idle_goals`). Its card in Duties carries a Built-in tag and the last duty job's name, and its cadence and pause are the chat's check-in setting, the same one the header's Check-in control writes. Every duty card edits its cadence (every N minutes or a daily time) and pauses (`POST api/threads/<id>/duties` with `action: "schedule"`). A standing duty runs the same way: its precheck, then one duty job named like `chat health 23:07` with the flagged items, the output file, a repeat miss and a precheck error in its brief. `node --import tsx scripts/duties/remove.ts --name "<name>" [--chat <id>]` deletes a duty with its runs and saved outputs. A correction in the ledger can name a handoff (`handoff: { to, topics, with?, env? }`, correction c7: machine work goes to ops guy): an open step in any other chat whose text names a topic as whole words inside the handoff's scope (`scopeMisses`: one of its `with` words, such as the services the rule names, and one of its `env` environments, local, staging or prod, named by the step or the nearest item above it; c36 takes only local uptime checks; not one that says it was handed off, or whose owner or `waitFor` names the target) is listed with `pN "..." belongs to <to> (correction c7): hand it off with a message to that thread and remove it from this plan`. `node --import tsx scripts/corrections-fix.ts <id> --ref <sha> --status active` records a landed fix. A chat's schedule survives a service restart: its last check-in is read from the check-in memory at start, so restarts closer together than its interval do not keep it from ever checking in (10-09: three restarts in 16 minutes did). The memory keeps each plan item's last change (status, text, owner or wait; a note edit is no change, so a chase note does not hide a stall), so the first run dates an unseen item from the board's `updatedAt`. Separately, when a subagent ends a follow-up task (status unchanged, activity gone) and `repliedSinceTask` is false, the server steers, 90 s later if it is still quiet, `[job] <name> is waiting for you since HH:MM (last message: "...")` when the chat's transcript holds a message from it since its last wake (the message's time), else `[job] <name> ended at HH:MM with no report` (the job's last activity, local time, so two ends read as two events), once per end (two ends whose last activity is less than 60 s apart are one end, `NO_REPORT_SAME_END_MS`, unless a new message arrived). The daemon's own `rlm_child_terminal_notice` covers a first task that ends with no reply. A job (a subagent or a create_session root in the chat row's Agents list) whose last turn ended on a provider error, an abort, a stop mid-tool (a tool call or tool result the model never answered) or the output length limit, and that sent the chat no report since its last start (`repliedSinceTask`, else no message from it in the chat's transcript since its last user or agent message), is told at once, at the scheduler wake that reads it (`jobEnd`, `Chats.jobEndNote`): one plain steer `[job] <name> stopped on a provider error ("<first 120 characters>") at HH:MM and sent no report` (or `was aborted`, `stopped in the middle of a tool call`, `hit the output length limit`); the chat decides what to do. Each end is told once and kept in `check-ins.json` under `ends` (by child id or `thread:<sessionId>`, a week), so a restart does not repeat it, and the check-in counts it in `job_end_silent`. A transient failure goes to the job wake first, so a job it revives gets no line; a cancelled subagent, one the server holds no snapshot of, and an end more than 2 hours old when found (`JOB_END_NOTE_MAX_AGE_MS`) get none. Every 10 minutes per chat (`JOB_CLEANUP_EVERY_MS`) the scheduler deletes each finished job (`finishedJobs`: a direct subagent that is done, reported, quiet an hour, and owned by no open step nor named in an open step's `waitFor`) with the daemon's `delete_rlm_subagent`, once, with one log line, so its worker and Python kernel stop holding memory. The daemon check-in heartbeat of older builds is cleared on the next attach (a heartbeat whose prompt starts with `OLD_CHECK_IN`). While the plan has no open step (todo, doing, blocked), the check-in runs daily (`planCheckIn`, `IDLE_CHECK_IN_MS`; owner 10-22: "make it Default to daily if plan list is empty"), the header shows "Check-in daily" and the board panel names the interval the next open step brings back; the stored setting is unchanged, so the chat's own interval runs again from that step. The chat can change its own check-in with the chat_board `check_in` argument (`{ pause: "1h" | "tomorrow" | null, every_minutes }`, `chatCheckIn`): it writes the owner's `<data dir>/check-in-settings.json` with the same rules (whole minutes 1 to 240, "tomorrow" is the next 09:00), never pauses until resumed, and cannot pause or resume over a pause the owner set that is still in force (`pausedBy`); whoever writes later wins otherwise, so the owner's later choice replaces the chat's. The result's first line (`The chat set its check-in: paused until 2026-10-09 09:00`) shows in the feed as a notice line. A chat whose last turn ended in `error` or `aborted` (a 429, a connection error, a Stop), or whose provider retry holds input queued behind a failure, is stalled (`turnStall` in `src/chat-recovery.ts`); it gets no `[job]` notice, since a steer then waits in its queue unseen (chat-453e got 4 check-ins and 25 notices 2 h late; VP of CI sat 32 min in a 429 provider wait with 6 owner messages queued). Instead the scheduler restarts it through `ThreadHub.restart` (abort when a provider retry holds the turn, the steer, then `resume_queue`): a turn something else started gets `[check-in] Your last turn failed at HH:MM (<error>). Re-check the board and continue.` 5 minutes after the failure, then 10, then every 20; a failed owner turn (not a Stop) gets `[check-in] Your last turn failed at HH:MM (<error>). The owner's message is still unanswered: "<text>". Answer it first.` after 30 s, then 5, 10, 20 min, and that turn stays the owner's (`OWNER_RETRY_MARK`), so the answer is a bubble. While it waits, the feed shows `Turn failed (<error>). Retrying at HH:MM.` under the owner's message (the hub's `wait` event). A provider retry with nothing queued is left to the session. Never while the chat is paused. It reads `running` (a turn, compaction, command, retry or session action), not `busy`, because queued input counts as busy. A transient failure (the pool token command failed or hit Prime's 10 s limit, `Connection error.`, fetch failed, ECONNRESET, ETIMEDOUT, socket hang up; `failureCause`) restarts after 30 s, 1 min, 2 min, then 5, 10, 20 min (`TRANSIENT_RETRY_BACKOFF_MS`), owner turns still quoting the owner. The scheduler wakes every 30 s; a gap of more than 90 s between two wakes means the Mac slept (`wokeFromSleep`), and that wake restarts every chat with a transient stall at once and starts its schedule over. Claude account wait: when a chat on an Anthropic model stalls because no account can serve it (no account, or a 429, 401, Consumer Terms 400 or transient failure while `pi-pool ls` shows no usable Claude account, read at most once a minute by `claudeReader`), the chat keeps its selected provider, model and thinking level. The feed shows the provider failure and `Waiting for a Claude account until HH:MM. Your selected model stays unchanged.` when the pool gives a reset time. The scheduler retries on the existing schedule. An unreadable pool is unknown for 429 and transient failures, while a provider no-account error still shows the account wait. A chat on a non-Anthropic model stays on its selected model. Manual model or account changes restart a stalled turn at once. A thread that owns an open step, whose last turn failed and that still holds queued input, gets abort, a `continue` steer and `resume_queue` at the chat's check-in, then on the 5, 10, 20 min schedule. A job of a chat that is not paused (a subagent or create_session root in the chat row's Agents list) whose last turn ended in a transient failure gets the same wake, queued input or not, once per failure, on the transient schedule and at once after a sleep (`jobWake`); the scheduler reads a job again only when its activity changed or while a failure of it waits. While any chat or job of one works, the service holds a macOS idle-sleep assertion with one `caffeinate -i -w <service pid>` child, killed 2 minutes after nothing works and at close (`src/chat-awake.ts`); lid-close sleep still happens. A model change in the header or an account change in Accounts on a stalled thread applies at once: a chat restarts its turn on the new choice, a plain thread gets its provider retry stopped and its queue resumed, so the next send is not stuck behind the old wait.
- Origin: every row carries `origin: "user" | "agent"` and the sidebar hides agent-created sessions by default. The daemon records no creator, so `src/thread-origin.ts` decides, in order: an id in `<data dir>/threads.json` (every thread `POST api/threads` created, both kinds) or in `chats.json` is `user`; else the session file decides, `agent` when its first `session_info` precedes its first `session_state` (a `create` request with a name writes the name first; `rlm.create_session` names roots at create, a person's session is renamed later), with files that have no `session_state` falling back to the name preceding the first message; else `user`. A file's decision is kept once it has a `session_state` or `message` entry. Sessions a person created with a name through a `create` request outside this server (`prime-agent --name`) read as `agent`; so do named browser threads from before `threads.json` existed.

## HTTP API

All routes sit under the capability URL. A browser navigation the person typed or bookmarked to `http://127.0.0.1:<port>/` (`Sec-Fetch-Site: none`) redirects there; every other request to `/` gets 404. Writes need JSON, the page token in `X-Chat-Token`, and the exact `Origin` for the requested host, either loopback HTTP or the configured HTTPS origin.

The page opens one WebSocket, `api/ws?token=<page token>`, and carries every live feed on it. Each EventSource used one of the six HTTP/1.1 connections Chromium allows per host, so three tabs used them all and later requests queued. The upgrade needs the exact page Origin for the requested host and the page token, the same pair a POST needs. Messages are JSON text frames. The page sends `{"type":"subscribe","sub":1,"feed":"sessions","delta":true}`, `{"type":"subscribe","sub":2,"feed":"thread","id":"<thread id>"}`, `{"type":"subscribe","sub":3,"feed":"login"}`, `{"type":"subscribe","sub":4,"feed":"refresh"}` (the latest usage refresh per provider), `{"type":"subscribe","sub":5,"feed":"usage"}` (the Settings > Usage summary from LGTM or its error, once at subscribe and then every 5 s) and `{"type":"unsubscribe","sub":2}`. The service answers `{"sub":1,"event":"build"|"sessions"|"thread"|"login"|"refresh"|"usage","data":...}`, the same payloads as the SSE events, and sends `{"event":"ping"}` with a protocol ping every 25 s. The page drops a socket that is silent for 70 s, reconnects with backoff (0.5 s doubling to 30 s), reconnects at once when the tab becomes visible or the network returns, and subscribes every feed again, so each thread gets a fresh snapshot.

With `"delta":true` the sessions feed sends the whole list once and then `{"type":"sessions-delta","add","patch","remove","order"?,"tags","daemon"}` frames (`src/shared/sessions-delta.ts`). The list held 2556 rows and 1.4 MB on 10-18 and went out whole about once a second, about 250 KB/s per tab after compression, while the Mac in Korea reads this box at about 370 KB/s, so a thread snapshot waited 13 to 30 s behind old lists. A delta carries new rows, the changed fields of changed rows, the changed agents of a changed `agents` list, and the id order only when sorting by activity would not rebuild it, and nothing goes out when nothing changed.

## Phone access through Tailscale

The main chat instance (`~/.prime/agent/browser-chat`) opens on your other devices through Tailscale with no setup. Keep Tailscale connected on the Mac and the phone, signed in to the same tailnet. The tailnet needs MagicDNS and HTTPS Certificates turned on (DNS page of the Tailscale admin console).

```text
phone (tailnet) --https--> https://<mac>.<tailnet>.ts.net/<secret>/
                             Tailscale Serve on the Mac, port 443, path /
                               --> http://127.0.0.1:5182/<secret>/  (chat listener, loopback only)
```

- On start and every 60 s the service reads `tailscale status --json` and `tailscale serve status --json`. If `https://<mac>.<tailnet>.ts.net/` has no handler, it runs `tailscale serve --bg --https=443 http://127.0.0.1:5182`. A handler there that points anywhere else is never replaced; Settings shows the command that frees it.
- The service then requests `https://<mac>.<tailnet>.ts.net/<secret>/api/identity` from the Mac and checks that this instance answered. Settings shows the time and result of the last check.
- The phone link is `https://<mac>.<tailnet>.ts.net/<secret>/`. It stays the same across restarts. If the machine is renamed in Tailscale, the service follows the new name on its next check.
- Settings > Phone access has the link, a Copy button and a QR code. Scan it with the phone camera and bookmark the page. `sieun-pi chat status` also prints it as `Phone:`, and `/agent-chat` prints it under the local URL.
- Turning "Open from my devices on Tailscale" off removes only this chat's root handler (`tailscale serve --https=443 --set-path=/ off`) and the remote host stops working at once. The switches change only from a page opened on the Mac (`127.0.0.1`); a remote page sees them read-only.
- `chat start --public-origin tailscale|https://HOST|none` sets the same thing from the terminal while chat is stopped. An HTTPS origin is fixed and never touches Tailscale. Instances with `--data-dir`, or under a different HOME, start with phone access off. `SIEUN_PI_CHAT_AUTOMATIC=0` turns the automatic defaults off for the main instance too.

The listener stays on `127.0.0.1`. Only the current remote host is allowed, with matching HTTPS Origin and page-token checks for writes. Forwarded headers cannot add hosts. The service-stop API stays local-only. A cross-site link may open the secret chat page; cross-site API requests remain blocked. Assets and the WebSocket use relative URLs, so they pass through the same proxy.

Keep the full URL private. Anyone who can reach the service and has that URL can read chats and control agents. Tailscale Serve limits network access to devices on the tailnet; do not use Funnel or an unauthenticated public proxy. Other HTTPS reverse proxies must preserve Host, pass WebSocket upgrades on the chat path, and restrict who can connect. Keep the Mac awake.

## Slack

The main instance can sync a chat to a Slack channel, `#vp-<chat name>` and private by default. It uses Socket Mode: one outbound WebSocket from this Mac, no public URL.
The bridge is off by default. With no tokens it stays off and the service runs as before.
Sync is opt-in per chat and off for every chat by default. "Connect to Slack" at the top right of a chat opens the setup dialog: the channel name (prefilled, checked the way Slack checks it: lowercase letters, numbers, hyphens and underscores, at most 80 characters), private or public, or an existing channel the bot is in (a list when the bot can list channels, else a field for an id or `#name`). The Slack button next to poteto-mode on the new-chat screen opens the same dialog for a chat you are about to create.
A connected chat shows the Slack mark and `#name`; clicking it opens the same dialog on the channel, with an Open in Slack link, a rename, and "Stop syncing" behind a confirm. A click never turns sync off.
Connect is idempotent: a chat that is already synced keeps its channel, a name that is taken is reused when the bot is in that channel, and repeated or concurrent connects (a double click, two tabs) make one channel because the bridge runs one chat's actions in turn.
Stop syncing archives the channel. Archiving the chat (after its confirm) archives its channel too; unarchiving the chat opens the same channel again (a new one if Slack refuses).

- In: a message you write in a chat's channel is a steer to that chat, the same call as the browser composer. An hourglass reaction stays on it until the turn ends.
- Out: the lines the browser feed shows on the left: replies on turns you started and `tell_owner` pings. Job reports and the chat's own notes stay quiet. Messages you type in the browser are not copied to Slack.
- Only your member id, in the team the bot token belongs to, is accepted. Bot posts, edits and deletes are dropped.
- Each line is posted once, keyed by message timestamp plus `toolCallId`, so compaction does not repost. Lines from before a chat was linked are never posted.
- After a reconnect (the Mac slept) the bridge reads each channel with `conversations.history` since the last handled message, because Socket Mode does not replay missed events.
- State lives in `<data dir>/slack.json`: the workspace connection and one link per synced chat (`channelName`, `isPrivate`, `archived` while the chat is archived).
- Public channels need the `channels:manage`, `channels:read`, `channels:history` scopes and the `message.channels` event from the manifest; an app installed before 2026-10-09 has to be reinstalled from the manifest for them.
- A synced chat whose feed does not open (its session is gone) is parked: one log line, then a quiet retry after 1 minute, doubling up to 30 minutes, so a dead session costs no daemon attach on every catalog update.
- Sync became opt-in on 2026-10-08. At the first connect after that, the bridge unlinked and archived every channel it had linked before, except `#vp-slack-bridge-probe`, and recorded `opt-in-2026-10-08` under `migrations` in slack.json so it never runs again.
- Text only for now: files you attach in Slack are not forwarded.

Setup: create the app from [`slack-app-manifest.yaml`](slack-app-manifest.yaml) (the file lists the steps), install it, and add an app-level token with `connections:write`.
Save both tokens in the Keychain, never in the repository:

```sh
security add-generic-password -U -s sieun-pi-slack -a bot-token -w   # xoxb-
security add-generic-password -U -s sieun-pi-slack -a app-token -w   # xapp-
```

`SIEUN_PI_SLACK_BOT_TOKEN` and `SIEUN_PI_SLACK_APP_TOKEN` work instead, for example through `dotenvx run -- sieun-pi chat serve`.
Then open Settings > Slack on the Mac, enter your member id and turn on "Connect Slack". Then press "Connect to Slack" in each chat you want in Slack. The refresh button reads the tokens again without a restart.
Only the main instance runs the bridge, so a test instance never opens a second Socket Mode connection; `SIEUN_PI_SLACK=1` or `0` overrides that.
Anyone who can post as your Slack account can drive agents with full access to this Mac, and workspace admins can read the channels. Use 2FA on that account.

## Keep running

On macOS the main instance runs as the LaunchAgent `com.sieun.agent-chat` (`~/Library/LaunchAgents/com.sieun.agent-chat.plist`). The first `chat start` or `/agent-chat` writes and loads it, so there is nothing to install by hand.

- At login launchd starts `chat serve --supervised`. After a crash it restarts it within about 10 s. `chat stop` exits cleanly, so launchd leaves it stopped until `chat start`, `/agent-chat` or the next login.
- If another chat process already holds the port, the supervised process waits for it. It takes over when that process crashes and stays idle when it stops with `chat stop`.
- Settings > Phone access > "Keep the chat running" turns this off. That removes the plist; a process that launchd started keeps running until it stops.
- Output goes to `~/.prime/agent/browser-chat/service.log`.
- The chat keeps the Prime Agent daemon running (`src/chat-daemon.ts`). Nothing else starts the daemon at login, so without this the chat came up after a reboot with no daemon until a terminal ran `prime-agent`. When the socket does not answer, the chat starts the daemon the way the official CLI does when a command finds none: the installed launcher `${PRIME_AGENT_INSTALL_DIR:-${XDG_DATA_HOME:-~/.local/share}/prime-agent}/bin/prime-agent` (the link the installer moves to each new release, so an update is followed with no path in the chat), else `prime-agent` on PATH, run as `--mode daemon --daemon-socket <socket>`, detached in its own process group, from the home folder. It then waits up to 30 s for the socket.
- The daemon gets the variables an interactive login shell exports (`$SHELL -i -l -c 'env -0'`, 15 s limit), the same ones a terminal would give it: launchd starts the chat with a bare PATH and none of the tokens the shell startup files export. A shell that fails or hangs falls back to the chat's own variables and the log line says so. Daemon-internal variables (`PRIME_AGENT_INTERNAL_*`) are dropped, as the official launcher drops them.
- One daemon per socket: the chat never starts one while the socket answers, and the daemon itself holds the `<socket>.lock` lease (refreshed every second, stale after 5 s) and refuses a socket in use. Two starters that race leave one daemon; the loser exits after it waits for the lease. A socket and lock left by a power-off are taken over after 5 s.
- A failed start is tried again after 2, 4, 8, 16, 32 s and then every 60 s. The chat also holds one connection to the daemon; when it closes (a crash, `prime-agent shutdown`), the chat checks again after 3 s and starts the daemon if nothing answers. Each attempt and each lost connection writes one line to `service.log`. The daemon outlives the chat: stopping or restarting the chat, or launchd stopping its job, leaves it running.
- Only the main instance does this. `SIEUN_PI_CHAT_START_DAEMON=1` turns it on for another instance, `0` turns it off. `chat status` prints whether the daemon answers.
- Only the main instance adopts chats at start: it pins every chat in `chats.json`, sets its steering, reloads a stale extension and scans the session files for chats the index lost. Any other instance (`--data-dir`, a changed HOME) acts only on the chats it created, listed in `<data dir>/own-chats.json`, even if its `chats.json` is a copy of the live one. `--no-adopt` keeps any instance, the main one too, to its own chats. Tests pass `--no-adopt`.
- A serve outside the live data dir (`~/.prime/agent/browser-chat` under the account's real home), or one started with `chat serve --scratch`, only reads. It starts no wakes, spawn briefs, check-ins, duties, job cleanup, duty archives, interrupted-job resumes, adopts, pool priority or turn-queue writes, SDK update, Slack, Tailscale, daemon start or login item, and it refuses `--adopt-live`. On 10-18 a CPU profile serve on a copy of browser-chat woke 3 live jobs and relayed 2 wakes through their parents at 08:25Z. `test/scratch-serve-read-only.test.ts` runs a serve against a fake daemon socket and a fake pi-pool and fails on any command that acts on a session.
- Every daemon command of a scratch serve goes through a socket in front of the daemon (`src/read-only-daemon.ts`) that passes only reads (`DAEMON_READS`: the session lists, the roster, the heartbeat lists and the `get_*` reads) and answers any other command with a failure. A scratch serve opens every thread from its session file and never attaches or resumes one, so it sends no attach, reload, restart, model or thinking set, steer or message. At 12:17Z on 10-18 a `--scratch` serve on a copy of browser-chat and the live socket opened 01a14d31, which its copied `own-chats.json` named, and its build-change reload rebuilt that chat's Python kernel.
- A scratch serve refuses the live daemon socket (the default `/tmp/prime-agent-<uid>/daemon.sock`, compared by real path) unless it is started with `--live-reads-only`, and with that flag it still sends only reads. `test/scratch-serve-live-chat.test.ts` opens an owned chat on an older build against a fake daemon and fails on any attach or reload, and checks the live socket refusal.

## Mac app

The chat installs as an app from Chrome (or another Chromium browser that offers Install; Aside cannot install web apps) with no native build: its own window and a Dock icon that survive reboots.

- The page links `manifest.webmanifest` (`appManifest` in `src/chat-assets.ts`): name "Prime Agent chat", `display: standalone`, and `id`, `start_url` and `scope` all `./`, so the app opens the capability URL it was installed from and one capability is one app. The icons (a white four-point spark on a violet tile) are drawn in code by `src/chat-icon.ts` on first request: 192 and 512 px on the macOS icon grid, a full-bleed 512 px maskable icon, a 180 px Apple touch icon for a phone home screen, and 32 and 64 px favicons drawn edge to edge for the tab. The page policy adds only `manifest-src 'self'`.
- Install: open the chat URL (`roles.chat.url` in `~/.config/sieun-pi/hosts.json` plus the capability in `~/.config/sieun-pi/chat-access.json`) in the owner's own Chrome profile and click the install icon in the address bar, then Install. Chrome puts `Prime Agent chat.app` in `~/Applications/Chrome Apps.localized` and opens it as its own window with a Dock icon. An agent can press both buttons through cua-driver accessibility clicks, with no cursor move. Do not install it into a separate `--user-data-dir`: that app starts a second Chrome with its own profile, which shows up as a plain Chrome window with tabs (seen 10-18). The manifest id `./` resolves against the origin, so Chrome keeps one app per chat origin.
- On a tailnet device of the machine's owner, the bare `https://<machine>.<tailnet>.ts.net/` redirects to the capability URL, so the app installs from that address. The chat checks the `Tailscale-User-Login` header that tailscale serve sets against the machine owner's login from `tailscale status --json`; other logins, funnel visitors and non-navigation requests get 404. On us-metal02 the edge Caddy also sends `http://us-metal02-dev/` (the MagicDNS short name) to that root.
- `sieun-pi open` (the same as `sieun-pi chat open`) opens the chat host's URL when `~/.config/sieun-pi/hosts.json` puts the chat role on another box (the URL from `roles.chat.url`, the capability from `~/.config/sieun-pi/chat-access.json`). Otherwise it starts the chat if needed (the login item for the main instance). It then opens the installed app window, else the URL in the default browser. It finds the app by the start URL that Chromium writes into the app bundle (`CrAppModeShortcutURL` in `~/Applications/<Browser> Apps.localized/<App>.app/Contents/Info.plist`), so it needs no Prime Agent session and works for whichever browser installed it.
- Settings > Phone access > "Open the app at login" (on by default, `openAppAtLogin` in the chat configuration) opens the installed app window once after each login. The first `chat serve --supervised` of a boot waits until its own `api/identity` answers, then runs `/usr/bin/open` on the app bundle. It keeps the boot time (`sysctl kern.boottime`) in `<data dir>/login-window.json`, so a crash restart, an exit-75 update restart or `chat start` later in the same boot opens nothing. Two readings within 10 s count as one boot, because macOS moves `kern.boottime` when it corrects the clock. That first start decides for the whole boot: a switch turned on later opens the window at the next login. With no installed app it opens nothing, no browser tab either, and writes one line to `service.log`. The note under the switch says what the next login does: "Opens <app> once after each login", or "Install the chat as an app from Chrome first". It needs "Keep the chat running", changes only from a page on `127.0.0.1` like the other switches, and exists only on the main instance; `SIEUN_PI_CHAT_OPEN_AT_LOGIN=1` gives another instance the switch and makes its `serve` act as a login start, `0` turns it off.
- After a reboot: launchd starts the chat at login, the chat starts the daemon, and once the chat answers it opens the app window at the same URL (the bullet above). With that switch off, open the app from the Dock or with `sieun-pi open`. A window the browser restored before the chat answered shows the browser's connection error; reload it with Cmd+R.

## Limits

- Message text up to 32,000 characters. Up to 4 images per message, 3 MiB each, 8 MiB total, PNG, JPEG, GIF or WebP.
- Extension commands that need terminal dialogs are refused with a message. Prompt and skill commands work.
- The image store is in memory and bounded, so an image URL can expire after a restart. Reopen the thread to refresh it.
