# apps/chat API

The chat server serves every endpoint under `/api` on 127.0.0.1:5184, one WebSocket at `/api/live`, and the built web client (`web/dist`) for every other path, with `index.html` as the fallback.
Every shape lives in `web/src/lib/api/types.ts`, which the server imports too, so this file names shapes and does not repeat them.
Pages call the server through `web/src/lib/api` (`import { api, timeline, agents } from "$lib/api"`) and never through `fetch` of their own.

## Run it

1. `npm install` in `apps/chat`, once.
2. `npm run fixture` runs the server on 127.0.0.1:5186 with a seeded fake host and a fresh data dir in /tmp, with no pi-host.
3. `npm start` runs it on 127.0.0.1:5184 against pi-host's socket `$XDG_RUNTIME_DIR/pi-host/host.sock` with data dir `~/.pi/agent/chat`.
4. The flags are `--port`, `--listen`, `--data-dir`, `--socket`, `--fixture` and `--web-dir`.
5. `npm test` runs the HTTP specs in `test/server/`, and `npm run typecheck` checks the server and `lib/api`.

## Ids

| Id | Form | Example |
|---|---|---|
| Agent | `ag_<slug>` | `ag_vent` |
| Agent's DM room | `dm_<slug>` | `dm_vent` |
| Work thread, root job thread, or a root chat no agent holds yet | pi-host thread id | `0f1e0000-0000-4000-8000-000000000001` |
| Job inside a thread | `<thread>:<conversation>` | `0f1e...0001:14` |
| Channel | `ch_<8 hex>` (the fixture's are `ch_cutover` and `ch_general`) | `ch_1a2b3c4d` |
| Solo room | `so_<8 hex>` | `so_0f1e0001` |
| Thread item | `e<entry>` for an input, `t<entry of its input>` for a turn | `e12`, `t12` |
| Room post (DM, channel or Solo room) | `p<seq>` | `p7` |

1. An agent (`agents.json`, `server/agents.ts`) has one main work thread, its root job threads, and one DM room. `/api/c/dm_<slug>` opens the DM, and `/api/c/<work thread id>` opens the work thread's transcript. A thread id of an agent's work thread or root job resolves to the agent wherever an agent id is taken, and a principal names the agent (`ag_<slug>`). A thread is an agent only through its record, which `POST /api/agents` or the migrate CLI (`scripts/migrate-agents.ts`) writes; the server never registers a root chat on its own, and the CLI skips an untitled one ("New thread", "Untitled" or no name).
2. An agent split into work and comm (agent-model.md phase 4) also has one comm thread per room, in its record's `comm`: its DM's, and one for each channel and Solo room whose post reached it (phase 5). The comm thread takes the room's posts and speaks in the room, and the work thread does the work. A comm thread id resolves to its agent for the board, check-in, folder and config routes, opens as a transcript by its id, and is never listed as an agent, a job or a solo chat.
3. The owner's principal id is `owner`.
4. A turn's id is the id of the input it answers, so the live turn keeps one id from the moment the input lands.
5. A pending send is `r:<requestId>` until its real item arrives: an input with its text in a thread, or the post with its `requestId` in a channel.

1. A DM row is one per agent that is not archived, `dm_<slug>`, with `agent` its agent id, `status` working while any of its threads runs, `preview` the newest post, and `unread` the agent's posts after the owner's read mark. The sidebar's `solo` group lists the Solo rooms first, open ones newest first, then closed ones (with `closedAt`), each with its `agenda`, then the root chats no agent holds. Such a root chat is a Solo row too, such as an untitled "New thread"; it stays solo until `POST /api/agents` or the migrate CLI makes it an agent. On its first thread list read after a start, the server drops each untitled record whose work thread is still untitled, with its aliases, and archives its DM room, so that chat is a Solo row again. An agent's work thread, a root job (a thread started for an agent, such as a duty run's thread) and a job inside a thread are kind `job` with their `parent` (a work thread's is its DM room): they never sit in the sidebar, show under their agent (the Jobs tab of its page on Agents), and open by link.
2. A DM is a room of posts the chat server stores in `<data dir>/rooms/dm_<slug>.jsonl` (`server/rooms.ts`), never a view of the thread. Its header has `workThread`, which "Open work thread" opens, and `readSeq`. Its items are `message` items, `p<seq>`, oldest first, and `before`, `after` and `around` take post ids. An owner post carries `requestId`, `send` and its delivery to the agent in `deliveries`: queued, delivered, stopped (the owner deleted the post before it went) or failed. A DM delivery never reads `answered`; only channel and Solo room deliveries do (item 15). An agent post carries `why` (the tell_owner call's), `work` (the work thread and `e<entry>` of the call, for "Show work") and `jobs` (the jobs its turn started, with live status).
3. For a split agent, the first delivery makes the comm thread ("<name> · DM", on the work thread's model and thinking level, in the agent's home), and every owner post and test send goes to it with `ownerTurn`. The feed reads the work thread to its end once and then reads only the comm thread, so a post's `work` names the comm turn. The DM row's `status` is working while the comm thread, the work thread or a job runs, and `commStatus` is the comm thread's own state. `AgentSummary.status` counts the work thread and its jobs only, and `AgentSummary.comm` lists each comm thread with its status.
4. A DM send writes the post and answers with it at once, shows it on every watching page, then delivers it to the agent's work thread as the owner's input (`requestId` `d:<post>:<agent>`, steer when busy, owner turn), retried with backoff and across a restart until pi-host takes it, or `failed` when pi-host refuses it for good. The agent answers through its speaking calls: each `tell_owner` or `send_message` with no `to` whose result says it went out becomes the agent's post, and a held or refused call posts nothing. A turn an old channel mention started in the work thread, from before phase 5, spoke to the channel, not the DM. An owner input typed in the work thread itself shows as his post once. A repeated `requestId`, or a re-read of the thread, lands nothing twice.
5. `around=<item id or e<entry>>` returns the page that holds that entry and `focus`, the id of the item that holds it, so a search hit opens at its message.
6. A thread page always starts at an input, so a turn never splits across two pages.
7. In a thread, `message` items are inputs, `turn` items hold the answer text, the steps (thinking and tool calls with name, one-line summary, status and `outputRef`) and the jobs the turn spawned, and `system` items are notes such as a compaction. A tool step's output is not in the page: `outputRef` names its conversation and tool result entry, and `GET /api/c/<conversation>/output/<entry>` answers `{ output }`, the text cut at 4,000 characters, when the owner opens it.
   An agent speaks to people only through its speaking tools, Prime's `tell_owner` (which pi-host's durable chat threads run from Prime's own chat extension) and pi-host's `send_message`, drawn alike (`SPEAKING_TOOLS` in `server/timeline.ts`). A turn of an agent that does holds `sent`, each call's text in order, which the page draws as one bubble each, and `text` is them joined by a blank line. Its other text becomes `note` steps beside its thinking and tool steps in the fold, and the calls themselves are not steps. A `tell_owner` call its guard held (its result opens with `Kept as a note, not sent`) is a `note` step, as Prime's feed shows it, and a refused one (an error result) is neither. A turn with `sent: []` sent nothing and draws only its fold, as "Worked quietly · N steps".
   A turn from before the conversation's first `send_message` call has no `sent`, and its own text is its bubble, so an agent that has never called the tool reads as before (`speaksThroughSendMessage` in `server/timeline.ts`). The server keeps the earliest call it has seen per conversation, so a page of quiet turns after it still reads as sent-only.
7. A turn's `jobs` hold each child conversation a `subagent` call made, which the page draws as a thread pill under the turn; a step's `job` names it too.
8. In a channel or Solo room every post is a `message` item; a channel root post carries `thread` with its reply count, last reply and authors, and replies come from `replies`. A Solo room has no threads.
9. Send takes `text`, `images` (the `{url, mimeType}` refs `POST /api/uploads` answered), `mentions` (agent ids), `threadRoot` for a channel reply, `whenBusy` (steer, the default, or followUp) and a `requestId`, and a repeated `requestId` lands once.
10. A thread send lands in the chat server and answers at once, as in Slack; no answer waits on pi-host. A thread send is written to the outbox (`<data dir>/outbox.jsonl`), shows on every watching page as the owner's message `r:<requestId>` with `send: "sending"`, and goes to pi-host behind the answer as the owner's input, retried with backoff until pi-host takes it (`send: "sent"`, also a steer that waits for the running turn), and across a restart. The item goes away (`items` with `removed`) once the input with its text shows in the conversation. pi-host refusing it for good (no thread, archived) makes it `send: "failed"` with `sendError`, until Retry or Discard. Each mention in it, and each mention in a DM post other than of the DM's own agent, goes to the mentioned agent's work thread as an agent message once pi-host has the send. Only a registered agent is a target: an agent id, its DM room, its work thread or its name. A mention of a job, a thread no agent holds or a name only a job has is not delivered.
11. A channel or Solo room post wakes every member whose `wakeOn` is `all`, which every member is unless muted, minus its author, as if it tagged each one. A channel thread reply wakes them too, and a member with `wakeOn: none` wakes on nothing. Each woken member gets one delivery to its comm thread for that room, never its work thread: the first delivery makes the comm thread, named `<agent> · #<channel>` or `<agent> · Solo <name>` (with the room id after it when another thread has that name), on the agent's work thread's model and thinking level. The request id is `d:<room>:<post>:<agent>`, retried with backoff and across a restart.
12. The input is one header line, a blank line and the post: `[#<channel> · post N from <author>[ (owner)] · hops H]`, or `[Solo "<name>" (so_x): <agenda, up to 300 characters> · with <members> · post N ...]`. A channel root post adds the root posts its member missed since the last root post it wrote or got, up to 5, under `(channel before this post)`, with their images, and a channel reply adds up to 5 earlier posts of its thread. An owner post goes in as the owner's turn (`ownerTurn`, steer when busy), and an agent post as an `agent.message` with `{from, via: <room>, post, hops}` that waits its turn (followUp).
13. Each comm thread's feed cursor sits in `rooms.json` under `commFeed`. Every `tell_owner` or `send_message` (with no `to`, or a `to` naming this room) whose result says it went out becomes the agent's post in the room, keyed `m:<thread>:<toolCallId>`, with `hops` one more than the post that started its turn (an owner post is hops 0), `mentions` from `@<agent name>` (any registered agent, member or not) and `@owner` in its text, and in a channel the thread of that post as `threadRoot`. The new post is delivered on like any other. A post 6 agent hops from the owner's last post gets `stopped` deliveries and is never submitted (`MAX_HOPS`, hard: money).
14. A closed Solo room, or an archived room, answers an owner post with 400 and a line that says to reopen or unarchive it, stores an agent post with no deliveries, and stops a delivery still on its way.
15. A channel or Solo room delivery reads `queued` until pi-host takes it, then `delivered`, `answered` (with `answer`, the member's first post after it in the same thread) once the member posted, `stopped` or `failed` (`group-rooms.ts` `publicDelivery`). A DM delivery never reads `answered`: it stays `delivered` after the agent's answer (`rooms.ts`). While a run waits for a working slot, the header and the `queue` events carry its place (`TurnPlace`), and watchers get `queue` events until it works.
16. As in Slack, a mention reaches any registered agent, member or not. One that is not a member gets the post in its comm thread for the room, made on demand, and answers in the room without joining it, so the @ typeahead offers every agent and marks the ones outside the room. An agent's post that names a registered agent as `@<name>` wakes it the same way. A mention of a job or a thread no agent holds is dropped from the post.

## Search

| Call | Endpoint | Returns |
|---|---|---|
| `api.search({q, from, where, in, after, before, sort, limit, cursor, brief})` | `GET /api/search` | `SearchResult`: `{hits, total, nextCursor, missing}`. `brief=1` leaves each hit's longer `text` out, for rows that show only the snippet. People and agents filter alike: the agents' search tools call this route with the same params. |
| `api.searchRecent({after})` | `GET /api/search/recent` | The newest room, channel and DM posts and the owner's own inputs as hits, newest first, each with up to 2,000 characters of its text as `snippet`. The Cmd K search matches each keystroke against them in the page (`web/src/pages/search/local-index.ts`) and shows those rows until the server's answer replaces them. `after` (epoch ms) gives only the messages written since. |

1. It covers every thread entry of every box and every channel and Solo room post, from one Meilisearch index (`server/search-engine.ts`). The server reads this box's pi-host `index.sqlite` (`--durable-index`, default `~/.prime/agent/pi-host/durable/index.sqlite`) on its own read-only connection, and every other box's rows through its agent relay's `durable_index_read` every 5 s, so a search asks no other box and still finds an offline box's threads. `missing` names a box whose newest rows may lack: one that is offline, or whose first read is still being indexed.
2. `q` may carry `from:`, `in:`, `after:`, `before:`, `has:` and `is:` tokens, and the separate params win over them. Each `from:` and `has:` token adds a value; `is:thread` is `place=threads`, and `is:saved` and `is:pinned` are `has` values. With no words but a filter, the search lists every message the filter keeps, newest first; with neither it lists nothing.
   `has` takes many of `link`, `reaction`, `pin` and `saved`, AND-ed: a room post with a link in its text, a reaction, the owner's pin, or an open item in the owner's Later. It keeps no thread entry.
3. `from` takes many values, as a comma list (`from=owner,ag_vent`) or repeated params, OR-ed: `owner`, `agents` (anyone but the owner), an agent id, or an agent's name with case ignored. An agent's hits are its posts, its agent messages, and every entry of its work thread and root job threads that the owner did not write. `in` is a conversation id, a channel or Solo room name with or without `#`, an agent's name for its DM, or a job's name as a hit shows it, case ignored. A room or agent wins over a job of the same name, and two jobs of one name are a 400 that lists their ids. `after` and `before` are YYYY-MM-DD in KST, with `before` excluding that day. An unknown value, or a name that fits two agents or places, is a 400 whose `error` names it.
4. `where` takes many of `root`, `thread` and `tool` the same way, all three when absent. `root` is a top-level post in a channel, Solo room or DM, and the owner's messages and the agent's words in a root chat no agent holds. `thread` is a reply in a channel thread. `tool` is everything inside agents' work: every entry of a work thread or job, and a root chat's tool output. `where=tool` replaced `type=tools` and `where=root,thread` replaced `type=messages`.
5. `sort` is relevance (default) or recent, and `limit` is 1 to 100 (default 20).
6. `total` is the exact count for the same filters (c191): Meilisearch counts every match with `maxTotalHits` at 100M. Each message counts and shows once: copies of one entry in several threads show from the unarchived one, comm threads are left out, since every room post is found in its room, and so is the copy of a channel post the router before phase 5 sent into a work thread.
7. A thread hit's `messageId` is its entry, `e<n>`, and a post's is `p<n>`. Each hit's `link` is the web route that opens it, built in `server/search.ts` `hitLink`: `#/c/<conversation>?m=e<n>` for an entry, `#/c/<room>?m=<post>` for a top-level post and `#/c/<room>?thread=<root>&m=<reply>` for a thread reply, whose page opens the thread pane at the reply. The room or job loads `items?around=<messageId>`, whose `focus` names the item that holds it. Search reads no thread file, so the first search after a start answers in under a second.
8. A snippet is escaped text whose only tags are `<mark>` around the matches, about 36 words of the message's human text (`server/search-snippet.ts`): an answer's own words before its tool calls, a `send_message` call's text as the agent's message rather than tool input, a tool's output with its JSON escapes and punctuation gone, and no routing or `[agent-message from X]` header. `text` holds up to 2,000 characters in the same form for "Show more", only when the message is longer.
9. Each hit says what it is. `role` is owner, agent, tool or system; a tool hit names its `tool`, and `inCall` says the match sits in a tool call's arguments rather than its output. `author.kind` is owner, agent or system (a check-in, job report or board note, with its label as the name), and an `[agent-message from X]` note names X. `conversation` carries `parent` (the agent a job or job DM belongs to) and `archived`, `where` says where it sits, and a thread reply carries `thread: {root, title}`, the root post and its first words, and `threadRoot`, the same root, until the search pages read `thread`.
10. By relevance, tool output (tier 1) ranks after every message, and a hit whose match sits only in a tool call sinks below the messages of its page.
11. The web client shows hits in the Cmd K rows (author, AGENT badge, place, kind and age) and on the full results page `#/search?q=&from=&in=&after=&before=&sort=&where=`, which Enter on the query opens. Each card reads the messages before and after it from `items?around=` (or `replies` for a thread reply) when it is expanded or keyboard-focused.

Each `/api/agents/:id/...` route has a `/api/threads/:id/...` twin that takes a thread id and resolves it to its agent, because pi-host's `chat_board` tool and the duty briefs name the thread; a root chat no agent holds yet keys by its thread id. `ForYouItem.chatId`, `BoardRow.chatId` and the `board` and `duties` events' `chatId` are agent ids, and `chatName` the agent's name.
2. An agent's board is the `chat.board` document of its work thread's root conversation in pi-host, changed through today's reducer (`lib/api/shared/chat-board.ts`). Its duties, their precheck state and its check-in live in `<data dir>/agents/<agent id>/`; an agent whose old `boards/<thread>/` folder the migration has not copied yet keeps using that folder.
3. Each owner op also reaches the work thread as a `[board] ...` input, as today.
4. A duty run works as in today's chat: the server runs the duty's precheck command with STATE_FILE, LAST_RUNS_FILE, OUTPUT_FILE and PRECHECK_MODE, judges its metrics, and records the run; when something is due (a miss, an error, an overrun or flagged items) it starts a duty job, a thread filed under the chat, whose `send_message` texts reach the chat as one `[duty <id>]` input from that job (a job that never called it sends its final answer, and "nothing to report" sends nothing).
5. A set takes a whole duty definition, Prime's duty JSON, and runs today's `upsertDuty` on the agent's duties (`lib/api/shared/chat-duties.ts`). A new name adds a duty, and a known name updates its definition and keeps its id, runs, run count and run state. A definition with no `schedule` keeps an updated duty's schedule, and a new duty runs daily at a free minute of the high morning band (`morningTime`), the band of a chat, among the daily times of every board here. Its `precheck.cwd` must be absolute. Prime's `scripts/duties/add.ts` resolves a relative one against the duty file's folder, and it sends the duty here when this server answers `GET /api/agents/<id>/config` for the chat it names, as `scripts/duties/remove.ts --chat` does for a remove. A remove deletes the duty, its runs and its precheck state files, and no later duty takes its id. A bad definition or an unknown duty answers 400, and an unknown agent or thread answers 404.
6. A due duty whose newest job still works, sleeps or waits for its first turn runs no precheck and starts no job, as a check-in does. It records one `skipped` run with the summary "skipped: previous run still working", which a later skip of the same wait replaces, and `last` reads the newest run that measured. While that job waits for a model account (`queued` in pi-pool's turn queue, or no model answer yet), its `DutyRow` carries `waitingForAccountSince`, the start of its run, and the card says "waiting for a model account since 12:01".
7. A duty job, or any agent, changes a board with `POST /api/threads/:id/board {actor: "agent", ops}`; only the owner answers a todo, and a refused op answers 400.
8. A due check-in or wake reaches the work thread as an input from `board`. `POST /api/threads/:id/wakes {id?, conversation?, on, note, since}` arms a wake, where `on` is the board skill's run, time or check wait; it answers `{wake, path, passes?}`, and `passes` means the check already exits 0. A wake is a JSON file in `<data dir>/wakes/` in the legacy chat's format, ticked by its own code (`server/wakes.ts`).

## Host seam

Every pi-host call goes through `server/host/` (`Host` in `types.ts`), which `pi-host.ts` implements over pi-host's `durable_*` socket commands and `fixture.ts` in memory.
While pi-host restarts, a call waits up to 30 s for it and then sends again, except `durable_create`, `durable_import` and a submit without a requestId, and live watches resume from the newest entry they delivered.
The default model and every model the pickers offer come from `config/allowed-models.ts` (c185).
